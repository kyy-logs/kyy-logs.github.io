一条https的url从按确认到数据渲染到页面这期间发生了什么

开始之前，我们先简单过一遍完整流程：

  1. 在浏览器中输入指定网页的 URL。
  2. 浏览器通过 DNS 协议，获取域名对应的 IP 地址。
  3. 浏览器根据 IP 地址和端口号，向目标服务器发起一个 TCP 连接请求。
  4. 浏览器在 TCP 连接上，向服务器发送一个 HTTP 请求报文，请求获取网页的内容。
  5. 服务器收到 HTTP 请求报文后，处理请求，并返回 HTTP 响应报文给浏览器。
  6. 浏览器收到 HTTP 响应报文后，解析响应体中的 HTML 代码，渲染网页的结构和样式，同时根据 HTML 中的其他资源的 URL（如图片、CSS、JS 等），再次发起 HTTP 请求，获取这些资源的内容，直到网页完全加载显示。
  7. 浏览器在不需要和服务器通信时，可以主动关闭 TCP 连接，或者等待服务器的关闭请求

应用层

一切的开始——打开浏览器，在地址栏输入 URL，回车确认。那么，什么是 URL？访问 URL 有什么用？

URL

URL（Uniform Resource Locators），即统一资源定位器。网络上的所有资源都靠 URL 来定位，每一个文件就对应着一个 URL，就像是路径地址。理论上，文件资源和 URL 一一对应。实际上也有例外，比如某些 URL 指向的文件已经被重定位到另一个位置，这样就有多个 URL 指向同一个文件。

  1. 协议。URL 的前缀通常表示了该网址采用了何种应用层协议，通常有两种——HTTP 和 HTTPS。当然也有一些不太常见的前缀头，比如文件传输时用到的ftp:。
  2. 域名。域名便是访问网址的通用名，这里也有可能是网址的 IP 地址，域名可以理解为 IP 地址的可读版本，毕竟绝大部分人都不会选择记住一个网址的 IP 地址。
  3. 端口。如果指明了访问网址的端口的话，端口会紧跟在域名后面，并用一个冒号隔开。
  4. 资源路径。域名（端口）后紧跟的就是资源路径，从第一个/开始，表示从服务器上根目录开始进行索引到的文件路径，上图中要访问的文件就是服务器根目录下/path/to/myfile.html。早先的设计是该文件通常物理存储于服务器主机上，但现在随着网络技术的进步，该文件不一定会物理存储在服务器主机上，有可能存放在云上，而文件路径也有可能是虚拟的（遵循某种规则）。
  5. 参数。参数是浏览器在向服务器提交请求时，在 URL 中附带的参数。服务器解析请求时，会提取这些参数。参数采用键值对的形式key=value，每一个键值对使用&隔开。参数的具体含义和请求操作的具体方法有关。
  6. 锚点。锚点顾名思义，是在要访问的页面上的一个锚。要访问的页面大部分都多于一页，如果指定了锚点，那么在客户端显示该网页是就会定位到锚点处，相当于一个小书签。值得一提的是，在 URL 中，锚点以#开头，并且不会作为请求的一部分发送给服务端。

DNS

键入了 URL 之后，第一个重头戏登场——DNS 服务器解析。DNS（Domain Name System）域名系统，要解决的是 域名和 IP 地址的映射问题 。毕竟，域名只是一个网址便于记住的名字，而网址真正存在的地址其实是 IP 地址。

HTTP/HTTPS

利用 DNS 拿到了目标主机的 IP 地址之后，浏览器便可以向目标 IP 地址发送 HTTP 报文，请求需要的资源了。在这里，根据目标网站的不同，请求报文可能是 HTTP 协议或安全性增强的 HTTPS 协议。

传输层

由于 HTTP 协议是基于 TCP 协议的，在应用层的数据封装好以后，要交给传输层，经 TCP 协议继续封装。

TCP 协议保证了数据传输的可靠性，是数据包传输的主力协议。

网络层

终于，来到网络层，此时我们的主机不再是和另一台主机进行交互了，而是在和中间系统进行交互。也就是说，应用层和传输层都是端到端的协议，而网络层及以下都是中间件的协议了。

网络层的的核心功能——转发与路由，必会！！！如果面试官问到了网络层，而你恰好又什么都不会的话，最最起码要说出这五个字——转发与路由。

  • 转发：将分组从路由器的输入端口转移到合适的输出端口。
  • 路由：确定分组从源到目的经过的路径。

系统进程和线程有什么区别？进程和线程的关系,协程了解吗？（进程和线程的区别(超详细)-CSDN博客）（什么是协程？ - 知乎）

1. 核心定义

  • 进程 (Process)：是操作系统进行资源分配的最小单位。
    • 你可以把它看作是一个正在运行的程序实例（比如你打开了一个 QQ）。
  • 线程 (Thread)：是操作系统进行任务调度和执行的最小单位。
    • 它是进程内部的一条执行路径（比如 QQ 里的一个线程负责接收消息，一个线程负责显示界面）。

2. 资源拥有

  • 进程：拥有独立的内存空间（代码段、数据段、堆等）。进程之间相互隔离，互不干扰。
  • 线程：共享所属进程的内存空间和资源（如堆、全局变量、文件句柄），但拥有自己独立的栈和程序计数器（为了记录执行到了哪里）。

3. 开销与切换

  • 进程：创建和销毁的开销大（要分配/回收内存），切换上下文慢（涉及页表切换、TLB 刷新）。
  • 线程：创建和销毁的开销小（主要就是个栈），切换上下文快（不用切页表）。
    • 所以也被称为“轻量级进程”。

4. 通信方式

  • 进程间通信 (IPC)：比较麻烦。需要用管道、消息队列、共享内存、Socket 等机制。
  • 线程间通信：非常方便。直接读写进程内的共享变量即可（但要注意线程安全，加锁）。

用协程做高并发需要注意什么?，协程是用户态的如何被操作系统调度?

在使用协程进行高并发开发时，核心必须遵循**“非阻塞”原则**，严禁在协程内调用同步 IO 操作以免卡死底层调度线程；同时要明确协程仅适用于 IO 密集型场景，CPU 密集型任务应剥离给独立线程池。由于协程创建极其廉价，容易瞬间引发流量突刺，因此必须配合信号量或连接池实施限流（背压保护）以防压垮下游，并严格处理并发安全（推荐用 Channel 或无锁设计）与异常超时，防止协程泄漏或僵死导致内存耗尽。

操作系统根本不知道协程的存在，它只负责调度“内核级线程”（Kernel Thread）。 协程是“寄生”在内核线程里面的，操作系统的调度器（OS Scheduler）看到的只是一个正在疯狂干活的线程，至于这个线程内部是在运行协程 A 还是协程 B，操作系统完全不关心，也无权干涉。

当你访问一个网站（如 www.example.com），整个过程如下：

  1. DNS 解析（应用层 - UDP 传输）
    • 浏览器检查本地缓存 → 操作系统缓存 → DNS 服务器查询域名对应的 IP 地址。
    • DNS 使用 UDP 协议（端口 53），属于应用层。
  2. TCP 连接（三次握手，传输层 - TCP）
    • 浏览器通过 TCP 协议（传输层），与目标服务器建立连接（SYN → SYN-ACK → ACK）。
    • HTTP/HTTPS 请求通过 TCP 传输。
  3. IP 数据传输（网络层 - IP 协议）
    • 目标服务器的 IP 地址确定后，数据包通过 IP 协议 进行路由传输。
  4. 数据链路层处理（数据链路层 - ARP 协议）
    • 在同一局域网内，使用 ARP（地址解析协议） 查询目标 IP 对应的 MAC 地址，实现数据包的最终传输。

用户态和内核态的区别，用户态和内核态是怎么进行切换的,系统调用的原理

  • 用户空间（User Space）：操作系统为用户程序（如应用软件）提供的内存区域，用户只能在这一空间中操作，无法直接访问硬件资源。
  • 内核空间（Kernel Space）：由操作系统内核管理的内存区域，用于存放内核代码、驱动程序、内核数据结构等，拥有对系统资源的完全访问权限。
  • 用户态（User Mode）：指程序运行在用户空间中，具有受限的权限，不能直接访问硬件或执行特权指令。
  • 内核态（Kernel Mode）：指程序运行在内核空间中，拥有最高权限，可以操作硬件、管理内存、调度进程等。

用户态和内核态的转换

用户态切换到内核态的3种方式：a.系统调用 b.异常 c.外围设备的中断

系统调用的原理

系统调用是用户进程进入内核的接口层，它本身并非内核函数，但它是由内核函数实现的，进入内核后，不同的系统调用会找到相应的内核函数，这些内核函数被称为系统调用的“服务例程”。
比如系统调用getpid()实际调用的是服务例程sys_getpid()，也可以说，系统调用getpid()是服务例程sys_getpid()的“封装例程”。

系统调用基本概念

计算机的各种硬件资源是有限的，为了更好的管理这些资源，用户进程是不允许直接操作的，所有对这些资源的访问都必须由操作系统控制。为此操作系统为用户态运行的进程与硬件设备之间进行交互提供了一组接口，这组接口就是所谓的系统调用。

系统调用实质上就是函数调用，只不过调用的是系统函数，处于内核态而已。 用户在调用系统调用时会向内核传递一个系统调用号，然后系统调用处理程序通过此号从系统调用表中找到相应的内核函数执行，最后返回。

这些系统调用按功能大致可分为如下几类：

  • 设备管理：完成设备（输入输出设备和外部存储设备等）的请求或释放，以及设备启动等功能。

  • 文件管理：完成文件的读、写、创建及删除等功能。

  • 进程管理：进程的创建、撤销、阻塞、唤醒，进程间的通信等功能。

  • 内存管理：完成内存的分配、回收以及获取作业占用内存区大小及地址等功能。

系统调用和普通库函数调用非常相似，只是系统调用由操作系统内核提供，运行于内核态，而普通的库函数调用由函数库或用户自己提供，运行于用户态。

总结：系统调用是应用程序与操作系统之间进行交互的一种方式，通过系统调用，应用程序可以访问操作系统底层资源例如文件、设备、网络等。

系统调用过程

系统调用的过程可以简单分为以下几个步骤：

  1. 用户态的程序发起系统调用，因为系统调用中涉及一些特权指令（只能由操作系统内核态执行的指令），用户态程序权限不足，因此会中断执行，也就是 Trap（Trap 是一种中断）。
  2. 发生中断后，当前 CPU 执行的程序会中断，跳转到中断处理程序。内核程序开始执行，也就是开始处理系统调用。
  3. 内核处理完成后，主动触发 Trap，这样会再次发生中断，切换回用户态工作。

系统调用号

Linux系统有几百个系统调用，为了唯一的标识每一个系统调用，Linux为每一个系统调用定义了一个唯一的编号，这个编号就是系统调用号。

系统调用号的另一个目的是作为系统调用表的下标，当用户空间的进程执行一个系统调用的时侯，这个系统调用号就被用来指明到底是要执行那个系统调用。

系统调用表

为了把系统调用号与相应的服务例程关联起来，内核利用了一个系统调用表，存放在sys_call_table数组中，它是一个函数指针数组，每一个函数指针都指向其系统调用的封装例程，有NR_syscalls个表项，第n个表项包含系统调用号为n的服务例程的地址。

系统调用处理函数

系统调用最终还是会由内核函数完成，那么为什么不直接调用内核函数呢？
这是因为用户空间的程序无法直接执行内核代码，因为内核驻留在受保护的地址空间上，不允许用户进程在内核地址空间上读写。所以，应用程序会以某种方式通知系统，告诉内核需要执行一个函数调用，这种通知机制是靠软中断来实现的，通过引发一个异常来促使系统切换到内核态去执行异常处理程序。此时的异常处理程序就是所谓的系统调用处理程序。

Linux下系统调用原理

根据上文，我们知道Linux使用一个中断号来对应所有的系统调用，那么只有一个中断号，操作系统怎么知道是哪一个系统调用要被调用呢？
上文也提到过，系统调用拥有自己的系统调用号，系统调用表以及系统调用处理函数。一个调用号对应一个处理函数，通过处理函数和调用号在调用表中找到相应的系统调用。

Linux中，在用户态和内核态运行的进程使用的栈是不同的，分别叫做用户栈和内核栈， 两者各自负责相应特权级别状态下的函数调用。当进行系统调用时，进程不仅要从用户态切换到内核态，同时也要完成栈切换， 这样处于内核态的系统调用才能在内核栈上完成调用。系统调用返回时，还要切换回用户栈，继续完成用户态下的函数调用。

进程间如何通信，各自的优缺点。父子进程间如何通信,线程间的通信方式，哪种方式效率更高，为什么？

进程之间的通信方式，主要有一下几种

  1. 管道，包括匿名管道、命名管道
  2. 信号
  3. 信号量
  4. 消息队列
  5. 共享内存
  6. 本地套接字

1. 管道 (Pipe)

这是最古老、最简单的IPC形式，分为匿名管道和命名管道。

a. 匿名管道 (Anonymous Pipe)

核心特点：

  • 半双工（单向）：数据只能在一个方向上流动。一端用于写，另一端用于读。
  • 亲缘关系：只能用于具有亲缘关系的进程之间（通常是父子进程或兄弟进程）。
  • 内核缓冲区：它在内核中开辟了一块缓冲区，写入的数据暂存于此，直到被读取。
  • 生命周期：随进程的创建而建立，随进程的结束而消亡。

生活比喻：父子之间用一根临时的、只能从父亲这边通向儿子那边的水管说话。

缺点：

  • 局限于亲缘进程：这是其最大的限制。
  • 半双工：若要实现双向通信，需要创建两个管道。
  • 字节流：数据本身没有格式，需要通信双方事先约定好数据格式。

适用场景：在Shell中执行的命令，如 ls -l | grep .txt，其中 | 就是一个匿名管道，将ls的输出作为grep的输入。

b. 命名管道 (Named Pipe / FIFO)

核心特点：

  • 无亲缘关系：可以在任意两个进程之间通信，只要它们能访问同一个文件路径。
  • 文件系统实体：它在文件系统中以一个特殊文件的形式存在，进程通过读写这个文件来进行通信。
  • 生命周期：不随进程的结束而消亡，而是随文件的存在而存在，除非被显式删除。

生活比喻：公园里的一个公共传声筒，任何知道它位置的人都可以过去对着一头说话，另一头的人就能听到。

缺点：

  • 仍然是半双工（默认情况下）。
  • 仍然是字节流，不带消息边界。
  • 速度较慢，因为数据需要在内核和用户空间之间复制。

适用场景：同一台机器上的客户端-服务器应用，服务器创建一个FIFO，客户端通过它发送请求。

信号量

信号量是一个计数器，可以用来控制多个进程对共享资源的访问。它常作为一种锁机制，防止某进程正在访问共享资源时，其他进程也访问该资源。因此，主要作为进程间以及同一进程内不同线程之间的同步手段。

  • 同步工具：它本质上不是用来传输数据的，而是用来同步和互斥的，通常作为共享内存的辅助。
  • 计数器：可以把它看作一个计数器，控制着同时能访问某个共享资源的进程数量。
  • 原子操作：对信号量的P（等待）和V（释放）操作都是原子性的。

缺点：

  • 不能传输数据，只是一个控制机制。
  • 易造成死锁：如果信号量使用不当，很容易导致进程互相等待的死锁局面。

消息队列是消息的链表，存放在内核中并由消息队列标识符标识，消息队列克服了信号传递信息少，管道只能承载无格式字节流以及缓冲区大小受限等特点。消息队列起信箱作用，到了就挂在那里，需要的时候去取。消息队列提供了一种在两个不相关进程间传递数据的简单有效的方法。

共享内存( shared memory ) ：共享内存就是映射一段能被其他进程所访问的内存，这段共享内存由一个进程创建，但多个进程都可以访问。

缺点：

  • 同步问题：必须由程序员自己负责同步，通常需要配合信号量或互斥锁使用，这大大增加了编程的复杂性。

三、 为什么共享内存效率最高？（核心底层原理）

共享内存之所以快，是因为它实现了**“零拷贝（或最少拷贝）”**。

我们可以通过对比消息队列/管道与共享内存的数据传输过程来看出差异：

1. 普通 IPC 方式（如管道、消息队列）的数据流转：

假设进程 A 要发数据给进程 B：

  • 第 1 次拷贝：进程 A 将数据从它的用户态内存拷贝到内核态缓冲区（执行 write 系统调用）。
  • 第 2 次拷贝：内核将数据从内核缓冲区拷贝到进程 B 的用户态内存（进程 B 执行 read 系统调用）。
  • 开销：不仅有 2 次内存拷贝，还伴随着 2 次系统调用导致的用户态与内核态的上下文切换。

2. 共享内存方式的数据流转：

  • 原理：操作系统在物理内存中开辟一块区域，然后通过页表映射，将这块物理内存分别映射到进程 A 和进程 B 的虚拟地址空间中。
  • 过程：进程 A 往这块内存写数据，进程 B 立刻就能看到。
  • 开销：0 次内核拷贝。数据不需要在用户态和内核态之间搬运，也不需要频繁的系统调用。
  • 性能：速度几乎等同于访问进程自身的局部变量，只受硬件总线带宽限制。

详解一下线程上下文切换

1. 上下文切换的基本概念

上下文切换指的是保存当前线程的状态（上下文），然后恢复下一个线程的状态。这些状态包括线程的寄存器内容、程序计数器（Program Counter，PC）、堆栈指针（Stack Pointer，SP）等。上下文切换是操作系统调度线程或进程时的核心操作。

2. 上下文切换的过程

一个典型的线程上下文切换过程包括以下步骤：

  1. 保存当前线程的上下文：
    • 当前线程的寄存器状态（包括程序计数器、栈指针等）被保存到线程的栈或线程控制块（Thread Control Block，TCB）中。
    • 线程的资源使用信息（如 CPU 使用情况、优先级等）也可能被保存。
  2. 选择下一个线程：
    • 操作系统的调度器根据调度算法（如轮转法、优先级调度等）选择下一个要执行的线程。
  3. 恢复下一个线程的上下文：
    • 操作系统从下一个线程的 TCB 或栈中恢复其上下文，包括程序计数器和寄存器的内容。
    • 将 CPU 的控制权转交给下一个线程，继续从它上次停止的地方执行。

3.上下文切换的触发条件

上下文切换通常由以下几种情况触发：

  • 时间片到期： 在线程或进程调度的时间片耗尽时，操作系统会主动进行上下文切换，调度下一个线程执行。
  • I/O操作： 如果当前线程需要等待 I/O 操作（如文件读取、网络请求等）完成，它会被阻塞，操作系统会切换到另一个线程。
  • 线程优先级变化： 如果某个线程的优先级发生变化，操作系统可能会进行上下文切换，以便执行优先级更高的线程。
  • 同步原语： 在多线程程序中，当线程在访问共享资源时发生同步操作（如锁、信号量等），也可能触发上下文切换。

线程切换为什么消耗CPU资源

保存当前线程的上下文 + 加载目标线程的上下文 + 切换地址空间/堆栈/寄存器状态

这些操作虽然都是“低级”的指令级动作，但都需要 CPU 主动参与、停止当前工作并重新建立环境，并非“免费”操作。

1.什么是时间片

时间片（Time Slice），也称为 时间片轮转调度（Time-Slicing Scheduling），是 操作系统分时调度机制 中用于分配 CPU 执行时间的基本单位。

在 多任务操作系统（如 Windows、Linux）中，CPU 需要在多个进程/线程之间 快速切换，使用户感觉多个程序在“同时”运行。而实际上，CPU 在每个任务上执行一小段时间（即时间片），然后切换到下一个任务。

  1. 时间片的工作原理

时间片调度通常采用 轮转调度（Round Robin, RR），即：

  1. 操作系统将 所有就绪进程 组织成 就绪队列（Ready Queue）。
  2. 调度器（Scheduler）从队列中取出第一个进程 分配一个时间片（如 10ms）。
  3. 当时间片耗尽时：
    • 如果进程 已完成，则从队列中移除；
    • 如果进程 未完成，则被挂起并放回队列尾部，等待下一轮执行；
    • CPU 切换到下一个进程，继续执行。
  4. 该过程不断重复，使得所有进程都能被公平调度。

1.发起IO请求（系统调用，陷入内核态）

内核接到IO请求后，负责准备IO操作，比如：

  • 确定要读哪块磁盘
  • 检查用户提供的缓冲区是否合法

  1. 发起DMA传输（关键！）

  • 传统方式（无DMA）：

  • 现代方式（有DMA）：

    • DMA控制器被引入，CPU告诉DMA：

      「帮我从磁盘读这块数据，直接搬到内存地址xxx」

    • 然后CPU就可以去干别的事了！（DMA负责自动搬运数据）

  • 等调度器（CPU Scheduler）安排它重新运行，
  • 这时候，用户程序就能拿到读取的数据了！

线程和进程间的切换主要有什么？ 上下文和虚拟内存页表映射。

1. 进程切换 (Process Context Switch) —— “搬家”

进程切换是开销最大的，因为它相当于两个完全不同的世界在切换。

主要包括两部分：

  1. 虚拟内存空间的切换（最耗时）：
    • 切换页表 (Page Table)：每个进程都有自己独立的虚拟地址空间，所以必须切换页表目录的指针（CR3 寄存器）。
    • TLB 失效 (TLB Flush)：切换页表后，CPU 的 TLB (Translation Lookaside Buffer) 里缓存的旧进程的地址映射全部失效，必须清空。这会导致接下来的内存访问变慢，因为都要重新查页表（这是进程切换慢的根本原因）。
  2. 硬件上下文的切换：
    • 保存和恢复 CPU 寄存器（PC, SP 等）。
    • 保存和恢复内核栈。

2. 线程切换 (Thread Context Switch) —— “换个房间”

线程是依附于进程存在的，同一进程下的线程共享内存空间。

主要包括：

  1. 硬件上下文的切换：
    • 保存和恢复 CPU 寄存器（PC, SP 等），因为每个线程执行的代码位置不同。
    • 保存和恢复线程的私有栈。
  2. 什么不需要切？（快的原因）
    • 不切换虚拟内存空间：页表不用动。
    • TLB 不失效：CPU 的地址缓存依然有效，内存访问速度不减。

操作系统进程的调度过程

一、 进程的三种基本状态

首先，一个进程在其生命周期中，至少有三种基本状态：

  1. 就绪态 (Ready)：万事俱备，只欠 CPU。进程已经拿到了除 CPU 之外的所有资源，只要调度器分配给它时间片，它就能立刻运行。
  2. 运行态 (Running)：正在占用 CPU 运行。
  3. 阻塞态 (Blocked / Waiting)：进程因为等待某个事件（如等待 I/O、等待锁）而无法继续执行，主动让出了 CPU。

二、 调度的时机 (When)

什么时候会发生进程调度？

  • 进程正常终止。
  • 时间片用完（非抢占式调度没有这一条）。
  • 进程主动阻塞（如发起 I/O 请求）。
  • 高优先级的进程到来（抢占式调度）。

三、 调度的过程 (How)

进程调度由操作系统的 调度器 (Scheduler) 完成。

核心流程：

  1. 中断/系统调用：发生调度时机（如时间片用完，发生时钟中断）。
  2. 上下文切换 (Context Switch)：
    • 保存现场：把当前正在运行的进程的硬件上下文（PC 寄存器、栈指针、通用寄存器等）保存到它的 PCB (进程控制块) 中。
    • 更新状态：将该进程的状态从“运行态”改为“就绪态”或“阻塞态”，并将其放入对应的队列。
  3. 选择新进程 (Scheduling)：
    • 调度器根据调度算法，从就绪队列 (Ready Queue) 中挑选一个最合适的进程。
  4. 恢复现场：
    • 将新选中进程的 PCB 中的上下文信息，加载回 CPU 的寄存器中。
    • 更新其状态为“运行态”。
  5. 继续执行：CPU 从新进程上次中断的地方继续执行。

四、 常见的调度算法 (Which)

  1. 先来先服务 (FCFS, First-Come First-Served)：
    • 规则：按进程到达就绪队列的顺序调度。
    • 缺点：对短作业不友好（前面有个长任务，后面一堆短任务得等着）。
  2. 短作业优先 (SJF, Shortest Job First)：
    • 规则：优先调度预计运行时间最短的进程。
    • 优点：平均等待时间最短。
    • 缺点：对长作业不友好（可能饿死），且需要预测运行时间。
  3. 时间片轮转 (RR, Round-Robin)：
    • 规则：给每个进程分配一个固定的时间片（如 10ms）。时间片用完就强制切换，把进程放到队尾。
    • 优点：公平，响应快，适合分时系统。
    • 缺点：上下文切换开销大。
  4. 多级反馈队列 (Multi-level Feedback Queue)：
    • 这是现代操作系统（如 Windows, Linux）实际使用的算法。
    • 规则：
      1. 设置多个就绪队列，优先级从高到低，时间片从小到大。
      2. 新进程先放最高优先级队列。
      3. 在高优先级队列里，按 FCFS 或 RR 调度。
      4. 如果时间片用完了还没执行完，就降级到下一个低优先级队列。
    • 优点：兼顾了**短作业（响应快）**和**长作业（不饿死）**。

虚拟内存和物理内存的区别？它们之间是怎么对应的？段式、页式、段页式分别是怎么寻址的

A. 段式寻址 (Segmentation)

  • 思想：按逻辑分块。代码段、数据段、栈段。

  • 地址结构：段号 + 段内偏移量。

  • 寻址过程：

    1. 查段表：根据段号找到该段在物理内存的起始地址。
    2. 计算：物理地址 = 起始地址 + 偏移量。
    • 缺点：会有外部碎片（内存里剩一堆小空隙塞不下大段）。

B. 页式寻址 (Paging) —— 主流

  • 思想：按物理分块。把内存切成固定的 4KB 小块（页）。

  • 地址结构：页号 + 页内偏移量。

  • 寻址过程：

    1. 查页表：根据页号找到对应的物理块号 (Frame Number)。
    2. 拼接：物理地址 = 物理块号 * 4KB + 偏移量。
    • 优点：没有外部碎片，内存利用率高。

C. 段页式寻址 (Segmented Paging)

  • 思想：结合两者。先分段（为了逻辑清晰），再在段里分页（为了好管理）。
  • 地址结构：段号 + 页号 + 页内偏移量。
  • 寻址过程（查两次表）：
    1. 查段表：根据段号找到该段对应的页表起始地址。
    2. 查页表：根据页号找到物理块号。
    3. 拼接：物理地址 = 物理块号 * 4KB + 偏移量。

请讲解一下四层网络负载均衡和七层网络负载均衡的区别，以及各自的应用场景。

1. 四层负载均衡（L4 Load Balancing）

  • 工作在哪层：OSI 模型的传输层 (Transport Layer)。
  • 依据什么转发：只看网络包的 “四元组”（源 IP、源端口、目的 IP、目的端口），加上 TCP/UDP 协议类型。
  • 工作机制：
    • 它就像一个**“无脑的快递分拣员”**。
    • 客户端和服务器之间建立的是一个完整的 TCP 连接。四层负载均衡器在中间收到 SYN 请求后，根据负载均衡算法（如轮询、Hash），直接修改数据包的目标 IP 地址（和端口）（即 NAT/DNAT 技术），然后原封不动地转发给后端的真实服务器。
    • 它不关心数据包里面的内容是什么（不知道是 HTTP 还是 FTP）。
  • 典型代表：LVS (Linux Virtual Server)、F5 硬件负载均衡、HAProxy (TCP 模式)。

2. 七层负载均衡（L7 Load Balancing）

  • 工作在哪层：OSI 模型的应用层 (Application Layer)。
  • 依据什么转发：除了 IP 和端口，它还能看懂应用层协议的内容（如 HTTP URL、Header、Cookie、User-Agent 等）。
  • 工作机制：
    • 它像一个**“大堂经理”**。
    • 它会先和客户端建立第一个 TCP 连接（完成三次握手），读取并解析完整的 HTTP 请求内容。
    • 然后根据请求内容（比如访问的是 /api 还是 /images），再和后端的真实服务器建立第二个 TCP 连接，把请求发送过去。
    • 客户端和服务器之间隔着两段 TCP 连接。
  • 典型代表：Nginx、HAProxy (HTTP 模式)、Envoy (Service Mesh)。

在大型互联网架构中，它们不是替代关系，而是上下游组合使用的关系。

1. 四层负载均衡的应用场景：

  • 总入口/大流量抗压：放在整个系统架构的最外层。因为四层 LB 性能极强，单台 LVS 可以轻松抗住几十万到上百万的并发连接。
  • 非 HTTP 协议代理：比如 MySQL 数据库集群代理、RabbitMQ 集群代理、Redis 集群代理，这些走的是 TCP 私有协议，只能用四层。

2. 七层负载均衡的应用场景：

  • 业务网关/微服务路由：通常挂在四层负载均衡的后面。由于能看懂 HTTP，所以适合做精细化的流量分发。
    • 动静分离：请求 /images 转给静态资源服务器，请求 /api 转给 Tomcat。
    • 灰度发布：根据 Cookie 或 Header 里的用户标签，把部分流量导向新版本服务。
  • HTTPS 卸载 (SSL Termination)：统一在 Nginx 层配置 SSL 证书，解密后再用明文 HTTP 传给后端 Tomcat，减轻后端服务器的 CPU 计算压力。

分钟内统计用户登陆失败次数 超过3次则封号 怎么设计

一、 核心方案设计（Redis to the Rescue）

方案 A：简单但有缺陷的 String 方案

  • 思路：利用 Redis 的 String 结构和 INCR 原子自增命令。
  • Key 设计：login_fail:user_id:yyyyMMddHHmm （将时间戳精确到分钟）
  • 流程：
    1. 用户登录失败，拼接 Key，执行 INCR key。
    2. 设置 EXPIRE key 60，让这个 Key 在 60 秒后自动过期。
    3. 每次 INCR 后，GET key 的值，如果 >= 3，则封号。
  • 致命缺陷：
    • 滑动窗口问题：它只能统计“固定的某一分钟”，比如 10:01:00 到 10:01:59。如果用户在 10:01:50、10:01:55、10:02:05 各失败一次，这个方案是无法检测出来的。

方案 B：精确但略复杂的 ZSet (Sorted Set) 方案 —— 推荐方案

  • 思路：利用 ZSet 的天然有序性来存储每次失败的时间戳。
  • Key 设计：login_fail_history:user_id
  • 流程：
    1. 记录失败：
      • 当用户登录失败时，将**当前时间戳（毫秒级）**作为 member 和 score，一起存入 ZSet。
      • ZADD login_fail_history:123 1721111111111 1721111111111
    2. 清理过期记录：
      • 为了防止 ZSet 无限膨胀，每次记录后，都要清理掉 1 分钟之前的数据。
      • 计算 1 分钟前的时间戳 t_1min_ago。
      • ZREMRANGEBYSCORE login_fail_history:123 0 t_1min_ago
    3. 统计次数：
      • 获取 ZSet 中元素的数量。
      • ZCARD login_fail_history:123
    4. 判断封号：
      • 如果 ZCARD 的结果 >= 3，执行封号操作。
  • 优势：完美实现了滑动窗口，无论在哪一秒钟，都能精确统计过去 60 秒的失败次数。

cpu内存访问的流程

第一阶段：发起请求与地址转换（虚拟到物理）

当 CPU 执行一条需要读取数据的指令（例如 MOV EAX, [0x00401000]）时，它使用的是虚拟地址（Virtual Address, VA）。

CPU 不能直接拿着虚拟地址去物理内存里找，必须先进行地址翻译。

1. 查 TLB（Translation Lookaside Buffer，页表缓存）

  • CEO 的动作：CEO 先翻看自己手边的小本子（TLB），看看最近有没有查过这个虚拟地址对应的物理地址。
  • TLB 命中（TLB Hit）：如果小本子里有记录，MMU（内存管理单元）瞬间就拿到了物理地址（Physical Address, PA）。这一步极快（不到 1 纳秒）。
  • TLB 缺失（TLB Miss）：如果小本子里没记录，CEO 只能去查完整的目录。

2. 查页表（Page Table Walk）—— 发生于 TLB Miss 时

  • CEO 的动作：CEO 去档案室查阅厚厚的《全局地址索引目录》（页表）。
  • MMU 会根据虚拟地址的页号，去**物理内存（主存）**中遍历多级页表（如四级页表）。
  • 页表项有效（Valid）：在页表中找到了对应的物理页帧号（Page Frame Number, PFN）。MMU 将其与虚拟地址的偏移量组合，得到最终的物理地址（PA）。同时，把这条记录写回 TLB，方便下次查。
  • 页表项无效（Invalid）：说明这个数据根本不在物理内存中（可能在硬盘的 Swap 分区，或者是一个非法的内存访问）。这时会触发缺页中断（Page Fault）（详见之前的解答，操作系统会介入，把数据从硬盘搬到内存，再更新页表）。

第二阶段：根据物理地址寻找数据（缓存层级）

拿到物理地址（PA）后，CPU 开始真正去取数据。它依然秉承“就近原则”，去**各级高速缓存（Cache）**中寻找。

现代 CPU 通常有三级缓存（L1、L2、L3），它们使用 SRAM 制造，速度远快于使用 DRAM 制造的物理内存（主存）。

3. 查 L1 Cache（一级缓存）

  • CEO 的动作：CEO 看看自己办公桌上的抽屉（L1 Cache）。L1 Cache 通常分为**指令缓存（L1i）**和**数据缓存（L1d）**，每个核心独享。
  • L1 命中（L1 Hit）：数据就在抽屉里！CPU 直接取走数据，耗时大约 1-2 个时钟周期（极快）。
  • L1 缺失（L1 Miss）：抽屉里没有，继续往下找。

4. 查 L2 Cache（二级缓存）

  • CEO 的动作：CEO 走出办公室，去同楼层的小型资料室（L2 Cache，通常也是每个核心独享）。
  • L2 命中（L2 Hit）：在资料室找到了！CPU 取走数据，同时**将这个数据及其相邻的一小块数据（Cache Line，通常是 64 字节）**复制一份放到 L1 Cache 中。耗时大约 3-10 个时钟周期。
  • L2 缺失（L2 Miss）：小型资料室也没有。

5. 查 L3 Cache（三级缓存）

  • CEO 的动作：CEO 下楼去整个公司共享的大型资料库（L3 Cache，所有核心共享）。
  • L3 命中（L3 Hit）：在大型资料库找到了。数据被取走，并依次存入 L2 和 L1 Cache。耗时大约 30-40 个时钟周期。
  • L3 缺失（L3 Miss）：连 L3 Cache 都没有，说明缓存彻底没命中（Cache Miss）。这被称为LLC Miss（Last Level Cache Miss）。

第三阶段：访问主存（DRAM）

这是 CPU 最不愿意见到的情况，因为访问主存的速度非常慢。

6. 访问物理内存（Main Memory）

  • CEO 的动作：CEO 只能派人坐车去郊外的超大型仓库（主存 RAM）取文件。
  • CPU 的**内存控制器（Memory Controller）**通过前端总线（FSB 或 QPI/UPI 等现代总线结构）向物理内存条发送读请求。
  • 物理内存根据物理地址定位到具体的数据，将数据通过总线传回 CPU。
  • 耗时极长：这个过程可能需要 100-300 个时钟周期，CPU 在这段时间里大部分处于等待状态（Stall）。
  • 缓存填充（Cache Fill）：取回来的数据（同样是一个 64 字节的 Cache Line），会被依次放入 L3、L2、L1 Cache 中，最后送到 CPU 的寄存器里供指令执行。

进程的寻址空间里面有什么

当一个程序被加载到内存中运行（成为一个进程）时，它在属于自己的那 3GB（或 2GB）的用户空间里，会按照极其严谨的结构进行布局。

从低地址（0x00000000）到高地址（0xBFFFFFFF），一个经典的进程内存模型（以 Linux 为例）通常包含以下段（Segment）：

1. 代码段（Text Segment / Code Segment）

  • 存放什么：存放程序编译后的机器指令（二进制代码）。
  • 特点：
    • 只读（Read-Only）：防止程序意外修改自己的指令。
    • 共享（Shared）：如果你打开了三个 Chrome 浏览器进程，它们在物理内存中其实共享同一份代码段，以节省内存。

2. 数据段（Data Segment）

  • 存放什么：存放程序中已初始化的全局变量和静态变量。
  • 例如：static int a = 10; 或者在函数外的 int b = 20;。

3. BSS 段（Block Started by Symbol）

  • 存放什么：存放程序中未初始化的全局变量和静态变量。
  • 例如：static int c;。
  • 特点：这部分在可执行文件中实际上是不占磁盘空间的，只是记录了需要多大空间。程序加载运行时，操作系统会自动将这块内存区域清零。

4. 堆区（Heap）

  • 存放什么：用于动态内存分配。在 C/C++ 中是通过 malloc/new 申请的内存；在 Java 中是通过 new 关键字创建的对象实体（存放在 JVM 堆中，而 JVM 堆本身就是向操作系统申请的这块 Heap 空间）。
  • 生长方向：堆区的内存是从低地址向高地址向上生长的。
  • 特点：空间大，生命周期由程序员（或垃圾回收器 GC）控制。如果申请了不释放，就会导致内存泄漏（Memory Leak）。

5. 内存映射段（Memory Mapping Segment / Mmap）

  • 存放什么：
    • 存放**动态链接库（Shared Libraries, 如 Linux 下的 .so，Windows 下的 .dll）**的代码和数据。
    • 通过 mmap() 系统调用映射的文件（常用于高效的文件读写或进程间通信 IPC）。
  • 位置：通常位于堆和栈之间。

6. 栈区（Stack）

  • 存放什么：用于维护函数调用的上下文。存放局部变量、函数参数、返回地址等。
  • 例如：在方法内部声明的 int x = 5;，或者传递给方法的参数。
  • 生长方向：栈区的内存是从高地址向低地址向下生长的。（与堆相反，它们相向而行，中间是空闲内存区）。
  • 特点：
    • 空间相对较小（Linux 下主线程默认通常是 8MB）。
    • 由编译器自动分配和释放（出作用域就销毁），速度极快。
    • 如果递归调用太深，或者在栈上分配了巨大的局部数组，就会导致两个区相撞，发生著名的栈溢出（Stack Overflow）。

7. 命令行参数和环境变量区

  • 位置：在用户空间的最高地址处（紧挨着内核空间）。
  • 存放什么：存放运行程序时传入的参数（如 ./my_program arg1 arg2 中的 arg1 等）以及系统的环境变量。

进程的内存布局(堆，栈，代码段（程序机器指令（可执行代码）），数据段（已初始化的全局变量、静态变量），BSS段（未初始化的)

IO模型：同步IO跟异步IO的概念是什么？有什么区别？阻塞IO跟非阻塞IO的概念是什么？（追问）同步/异步 与 阻塞/非阻塞 这四者之间的关系是什么？

  • 阻塞 I/O (Blocking I/O)
    • 概念：当我们发起一个 read() 系统调用时，如果内核发现数据还没准备好，那么这个发起调用的应用程序线程会被立刻挂起（阻塞/Block），让出 CPU 执行权，直到数据准备好并拷贝完成，read() 调用才会返回。
    • 比喻（去餐厅吃饭）：你点完菜后，就坐在座位上啥也不干，一直傻等，直到服务员把菜端到你面前，你才能继续做别的事。
    • 优点：代码写起来最简单、最直观。
    • 缺点：一个线程在同一时间只能处理一个 I/O 请求，并发能力极差。
  • 非阻塞 I/O (Non-blocking I/O)
    • 概念：当我们发起 read() 调用时，如果数据还没准备好，内核不会挂起你的线程，而是立刻返回一个错误码（如 EAGAIN/EWOULDBLOCK）。
    • 比喻：你点完菜后，不傻等。每隔一分钟就跑去问服务员：“菜好了没？” 服务员说“没好”，你就回去玩会儿手机；再说“没好”，你又回去玩会儿手机…直到服务员说“好了”，你才开始吃饭。
    • 缺点：这种**轮询（Polling）**的方式会极大地消耗 CPU 资源（因为你的线程一直在忙着问）。

追问三：同步 I/O vs. 异步 I/O (关注点：数据拷贝阶段谁来做？)

“‘同步’和‘异步’，描述的是当数据准备好后，负责把数据从内核拷贝到用户空间这个动作，到底是由谁来完成的。”

  • 同步 I/O (Synchronous I/O)
    • 概念：即使在非阻塞模式下，当轮询到数据已经准备好了，应用程序必须自己发起第二次系统调用，并且主动等待内核把数据拷贝到自己的用户空间内存中。在拷贝完成前，应用程序依然是阻塞的。
    • 比喻：服务员告诉你菜好了，但只是放在了出餐口。你必须自己走到出餐口，等着服务员把菜打包好，递到你手里，你才能走。
    • 关键点：阻塞 I/O、非阻塞 I/O、以及 I/O 多路复用（select/epoll）都属于同步 I/O 的范畴！ 因为它们在最终的“数据拷贝”阶段，都需要应用程序自己去等待和处理。
  • 异步 I/O (Asynchronous I/O)
    • 概念：这是最理想的模式。我们发起一个 aio_read() 调用后，立刻就能返回，然后去干别的事。
    • 比喻：你点完菜，告诉服务员：“菜好了直接送到我座位上”，然后你就戴上耳机专心玩游戏了。服务员不仅负责把菜做好，还负责把菜端到你面前。等菜到了，你只需要抬头吃就行了。
    • 关键点：从数据准备到数据拷贝的整个过程，都是由操作系统内核独立完成的。应用程序只需要在最后接收一个“完成通知（Callback）”即可。这是真正的“无等待”。

cas在操作系统上的底层实现

CAS 原理与实现：CAS 是原子操作，通过 CPU 提供的原子指令（如 x86 的 CMPXCHG 或 ARM 的 LDREX/STREX）实现，用户态直接操作内存并循环重试，实现无锁同步。

进程在执行fork操作的时候，子进程会继承父进程的什么信息？

第一部分：内存数据与运行状态 (Memory & Execution Context)

这是最核心的部分。子进程会继承父进程几乎所有的用户空间内存快照。

  1. 虚拟内存空间的完整克隆：
    • 代码段 (Text Segment)： 继承父进程执行的机器指令（代码）。（注意：代码段通常是只读的，所以父子进程在物理内存中实际上是共享同一份代码的。）
    • 数据段 (Data Segment) & BSS 段： 继承父进程中已初始化和未初始化的全局变量、静态变量。
    • 堆区 (Heap)： 继承父进程中通过 malloc/new 动态分配的内存数据。
    • 栈区 (Stack)： 继承父进程中所有的局部变量、方法调用栈和执行现场。
  2. CPU 寄存器状态：
    • 程序计数器 (PC / EIP)： 这是最关键的一点。子进程继承了父进程的 PC 值，这意味着子进程从 fork() 调用返回后的下一条指令开始执行，而不是从头开始运行程序。
    • 其他通用寄存器的值也会被继承。

【面试高分亮点：写时复制 COW】
“面试官，这里必须提一下，现代操作系统在克隆上述的数据段、堆和栈时，并不会立刻在物理内存中复制一份一模一样的数据（那样极其耗时且浪费内存）。
而是让父子进程的虚拟地址映射到同一块物理内存，并将这块内存标记为‘只读’。
只有当父进程或子进程试图**修改（Write）*某一块内存页时，内核才会触发缺页中断，真正为修改方在物理内存中拷贝一份该页的副本。这就是著名的*写时复制 (Copy-on-Write) 技术，它使得 fork() 的速度极快。”

第二部分：文件系统相关资源 (File System Resources)

这也是极其容易踩坑，且在实际并发编程中必须要处理好的部分。

  1. 打开的文件描述符 (File Descriptors, FD)：
    • 子进程会继承父进程所有已经打开的文件描述符表。
    • 深度理解： 这里的继承是指“浅拷贝”。父子进程的 FD 指向的是操作系统内核中同一个打开的文件表项（Open File Table Entry）。
    • 导致的现象： 这意味着父子进程共享相同的文件偏移量（File Offset）。如果父进程读了文件的前 10 个字节，子进程接着读，会从第 11 个字节开始读。如果两边同时往一个文件里写数据，内容会交错混合。
    • （Socket 也是文件描述符，所以子进程也能继承父进程建立的网络连接）。
  2. 当前工作目录 (Current Working Directory) 和根目录 (Root Directory)。
  3. 文件创建掩码 (umask)： 决定了新创建文件的默认权限。

第三部分：进程属性与控制信息 (Process Attributes & Control)

子进程会继承父进程大部分的环境和身份标识。

  1. 环境变量 (Environment Variables)： 如 PATH, HOME 等。
  2. 用户和组 ID： 继承真实的 UID (Real UID)、有效的 UID (Effective UID)、真实的 GID 等权限标识。
  3. 信号处理方式 (Signal Dispositions)：
    • 继承父进程对某个信号是“忽略”、“捕获”还是“默认处理”。
    • （注：虽然继承了处理方式，但父进程未决的挂起信号 pending signals 是不会被继承的，因为那属于父进程自己的未处理事件）。
  4. 资源限制 (Resource Limits)： 如通过 ulimit 设置的打开文件数上限、CPU 时间上限等。
  5. 控制终端 (Controlling Terminal) 和进程组 ID / 会话 ID。

面试进阶追问：子进程“没有”继承什么？（独有的信息）

为了展现知识的完整性，你可以主动提一下父子进程的不同点：

“虽然子进程几乎继承了所有，但为了在操作系统中区分它们，内核必须赋予子进程一些独有的、不继承的信息：

  1. 进程 ID (PID)： 子进程拥有系统分配的全新的、唯一的 PID。
  2. 父进程 ID (PPID)： 子进程的 PPID 会被设置为执行 fork() 的那个父进程的 PID。
  3. fork() 的返回值： 在父进程中，fork() 返回子进程的 PID；在子进程中，fork() 返回 0。这是我们在代码中写 if (pid == 0) 来区分父子进程逻辑的唯一依据。
  4. 资源统计信息清零： 子进程的 CPU 占用时间（tms_utime, tms_stime 等）、缺页中断次数等统计信息会被清零。
  5. 未决信号 (Pending Signals)： 父进程中尚未处理的信号不会被子进程继承。
  6. 文件锁 (Record Locks / File Locks)： 父进程在文件上加的锁，子进程不会继承（否则会引发严重的并发冲突）。

用户态和内核态之间转换的时候发生了什么？

当用户态切换到内核态的时候，实际上发生了一次非常严格的**“门禁式”**切换。为了保证安全性，操作系统并不是简单的“跳转”过去，而是经历了非常严谨的步骤：

转换的触发条件（什么情况下会发生？）

  1. 系统调用（System Call）： 用户程序主动请求内核服务，如 read(), write(), fork(), malloc() 等。
  2. 异常（Exception）： 当程序发生缺页中断（Page Fault）、除 0 等异常时。
  3. 硬件中断（Hardware Interrupt）： 如网卡收到数据包、键盘按键、时钟中断等。

转换的底层发生了什么？（具体的执行步骤）

当触发上述任一条件时，CPU 硬件和操作系统内核会协同完成以下“原子性”动作：

  1. 保存用户态现场（Context Save）：
    • CPU 暂停当前用户态程序的执行。
    • 将当前所有的**通用寄存器、程序计数器（PC，记录下一行代码）、栈指针（SP）压入内核栈（Kernel Stack）*中。（注意：是压入内核栈，而不是用户栈，这是为了防止用户程序恶意破坏现场！）*
  2. 栈的切换（Stack Switch）：
    • CPU 将栈指针寄存器（SP）从“用户栈”指向“内核栈”。此时程序已经脱离了用户程序自己的内存区域，处于内核的安全管控区。
  3. 特权级切换（Privilege Switch）：
    • CPU 硬件将特权级标志位（CPU 的 Mode Bit）由 Ring 3（用户态）切换为 Ring 0（内核态）。此时 CPU 才被允许执行特权指令。
  4. 定位并执行内核函数：
    • CPU 通过**中断向量表（Interrupt Vector Table）**找到对应的内核处理函数。例如如果是系统调用，会根据系统调用号（System Call Number）去中断向量表里找到对应的函数（如 sys_read）去执行真正的底层逻辑。
  5. 内核逻辑执行：
    • 执行内核代码，操作网卡、磁盘、分配内存等。
  6. 恢复现场并切回用户态（Context Restore）：
    • 内核执行完毕后，执行特殊的返回指令（如 iret）。
    • 将内核栈中保存的寄存器、PC、SP 弹出并重新加载回 CPU。
    • 将特权级由 Ring 0 切换回 Ring 3。
  7. 继续执行：
    • PC 指针指向用户程序原本被中断的位置，程序在用户态继续无缝执行。
