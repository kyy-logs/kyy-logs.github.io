TCP 如何实现可靠传输和流量控制？

（1）如何实现可靠传输？

TCP 的可靠传输不是靠单一机制完成的，而是一套“组合拳”，确保数据无差错、不丢失、不重复、且按序到达：

  1. 校验和（Checksum）： 检查数据在传输过程中是否发生了物理损坏（位错误），如果校验失败直接丢弃。
  2. 序列号与确认应答（Seq & ACK）：
    • 防乱序与去重： TCP 给每个字节都打上序号（Sequence Number），接收方可以根据序号重新排序，并丢弃重复收到的数据。
    • 确认机制： 接收方收到数据后，必须回传一个 ACK（确认号），告诉发送方“我收到了”。
  3. 重传机制： （如上题所述）通过超时重传和快速重传，解决报文在网络中丢失的问题。
  4. 连接管理： 通过“三次握手”建立可靠连接，通过“四次挥手”安全释放连接，确保双方都准备好收发数据。

（2）如何实现流量控制（Flow Control）？

核心目的： 防止“发送方发得太快”，导致“接收方处理不过来”从而撑爆接收方的缓存（针对的是端到端的接收能力）。
实现机制：滑动窗口（Sliding Window）

  1. 接收方在给发送方回传 ACK 报文时，会在 TCP 头部填入一个叫 rwnd（接收窗口，Receive Window） 的值。
  2. 这个值代表接收方目前还有多少空闲的缓存区可以接收数据。
  3. 发送方收到这个值后，会严格按照 rwnd 的大小来限制自己下一次发送的数据量。如果 rwnd=0，发送方就会停止发送，并启动“零窗口探测计时器”（如上一题所述）。

TCP 发送窗口如何根据接收窗口和拥塞情况动态调整，窗口结构如何维护变化？

（1）发送窗口的动态调整机制

发送方的**发送窗口（swnd, Send Window）**并不是单方面决定的，它受到“接收方处理能力”和“整个网络拥堵情况”的双重制约。
核心公式：发送窗口 swnd = min(接收窗口 rwnd, 拥塞窗口 cwnd)

  • 接收窗口（rwnd）： 来自接收方，反映接收方的缓存余量（流量控制）。
  • 拥塞窗口（cwnd，Congestion Window）： 是发送方自己维护的一个状态变量，反映当前网络的拥堵程度（拥塞控制）。
    • 慢启动（Slow Start）： 连接刚建立时，cwnd 从小开始，呈指数级增长。
    • 拥塞避免（Congestion Avoidance）： 当 cwnd 达到某个阈值时，改为线性增长，避免突然拥塞网络。
    • 网络拥塞发生时（丢包）： 如果发生超时重传，cwnd 瞬间降到极小值（如 1），重新慢启动；如果发生快速重传，cwnd 减半，进入“快速恢复”阶段。

结论： 发送方会取 rwnd 和 cwnd 中的较小值作为实际的发送窗口大小。谁的能力弱（接收方来不及，或网络塞车），就听谁的。

（2）窗口结构如何维护变化？

发送方的滑动窗口将数据分为四部分：

  1. 已发送且已确认（窗口左侧，不再关心）
  2. 已发送但未确认（占用窗口空间，随时准备重发）
  3. 允许发送但尚未发送（窗口内剩余的可用空间）
  4. 不允许发送（窗口右侧，必须等窗口向前滑动才能发送）

窗口的变化（滑动）：
当发送方收到接收方的 ACK 确认后，窗口的左边缘会向右移动（把“已确认”的数据移出窗口）。同时，根据接收方最新通告的 rwnd 大小，窗口的右边缘可能向右扩展（接收方处理完了旧数据，腾出了新空间），从而允许发送更多属于第 4 部分的数据。

为什么 HTTP/3 基于 QUIC，而不继续在 TCP 上优化？

  1. TCP 的“队头阻塞”问题无法彻底根除（最核心原因）：
    • HTTP/2 引入了“多路复用”，在一个 TCP 连接上可以并发跑多个 HTTP 请求。
    • 但是，TCP 的底层设计是保证数据的“严格有序”。如果在同一个 TCP 连接中，某个数据包丢了，TCP 会暂停把后续收到的所有数据交给应用层，直到丢失的包重传成功。
    • 这意味着，只要丢一个包，这个 TCP 连接上的所有 HTTP/2 请求全部卡死！这被称为 TCP 层的队头阻塞。
  2. 建连延迟太高（握手太慢）：
    • TCP 三次握手需要 1 个 RTT（往返时间）。如果加上 HTTPS 的 TLS 加密握手，又需要 1~2 个 RTT。用户打开网页的初始延迟很高。
    • QUIC 将传输层握手和加密层握手合二为一，可以实现 1-RTT 甚至 0-RTT（首次连接过以后，再次连接无需握手直接发数据）。
  3. 网络迁移体验差：
    • TCP 连接由“四元组”（源 IP、源端口、目的 IP、目的端口）标识。当你拿着手机从 4G 切换到 Wi-Fi 时，IP 地址变了，TCP 连接就会断开，必须重新建立连接（导致视频卡顿、游戏掉线）。
    • QUIC 使用一个 64 位的 Connection ID（连接标识符） 来识别连接，只要 ID 没变，即使 IP 变了，连接依然无缝继续。

HTTP 队头阻塞是什么？

队头阻塞（Head-of-Line Blocking, HoL），顾名思义，就像十字路口等红灯，排在第一辆的车（队头）如果出了故障不动，后面的车即使要去不同的方向，也被堵死在后面无法前行。

在 HTTP 的演进中，队头阻塞发生过两次“变异”：

1. HTTP/1.1 时代的“应用层”队头阻塞

  • 原因： HTTP/1.1 规定，在同一个 TCP 连接上，请求可以连续发（Pipelining），但服务器必须严格按照请求的顺序返回响应。
  • 表现： 浏览器发了 A、B 两个请求。如果 A 是一个需要服务器处理很久的复杂请求（或者 A 的响应数据极大），那么哪怕 B 只是一张很小的图片且早处理完了，B 也必须等 A 完全发送完毕后才能返回。
  • 当时的解决办法： 浏览器干脆对同一个域名同时开启 6 个 TCP 物理连接，绕过限制。

2. HTTP/2 时代的“传输层 (TCP)”队头阻塞

  • 改进： HTTP/2 引入了二进制分帧和多路复用，A 和 B 两个请求的数据可以切碎了混合在同一个 TCP 连接里发送，谁先处理完谁先发，彻底解决了 HTTP 层的队头阻塞。
  • 新问题（TCP 队头阻塞）： 如上文所述，所有的请求现在都挤在唯一的 1 个 TCP 连接里。TCP 看不到 A 和 B，它只看到一串字节流。一旦网络发生丢包（假设丢的是 A 的一个数据包），TCP 为了保证顺序，就会把后续收到的 B 的数据包也扣留在操作系统的缓存里不给浏览器，导致 B 也被无辜卡死。

HTTP/3 (QUIC) 的终极解决

QUIC 在底层原生支持了“流（Stream）”的概念。
在 QUIC 中，请求 A 和请求 B 是相互独立的流。如果 A 的数据包丢了，QUIC 只会暂停 A 的处理等待重传，而毫无关联的 B 的数据包会被直接放行给浏览器。至此，队头阻塞问题被彻底解决。

ping 的原理

**一句话总结：ping 命令的底层原理是基于网络层的 ICMP实现的。它通过向目标主机发送“回送请求（Echo Request）”报文，并等待接收目标主机返回的“回送应答（Echo Reply）”报文，从而判断两台主机之间的网络连通性以及计算往返时间（RTT）。

核心协议：ICMP 扮演了什么角色？

  • ICMP 是什么？
    • ICMP 是 IP 协议的“辅助协议”，它工作在 OSI 模型的网络层（和 IP 协议同层）。
    • 它的主要职责是在 IP 主机、路由器之间传递控制消息（比如：网络通不通、主机是否可达、路由是否异常等）。
    • 注意（易错点）： ICMP 不是传输层协议，它不需要端口号，也不使用 TCP 或 UDP，它是直接封装在 IP 数据包内部传输的。
  • Ping 用到了 ICMP 的哪两种报文？
    • ping 核心就利用了 ICMP 协议定义的不同 Type（类型）和 Code（代码）。
    • Echo Request (回送请求)： 发送方发出的探测包（Type = 8, Code = 0）。
    • Echo Reply (回送应答)： 接收方收到请求后，必须原样返回的数据包（Type = 0, Code = 0）。

2. Ping 的完整工作流程（以 ping 192.168.1.100 为例）

当你在终端敲下回车的那一刻，底层发生了一系列严密的交互：

第一步：构建 ICMP 请求包 (源主机发起)

  1. ping 程序首先构建一个 ICMP Echo Request 报文。
  2. 在这个报文里，会填入一些关键信息：
    • 标识符 (Identifier)： 通常是当前 ping 进程的 ID，用来区分这是哪个 ping 命令发出的包。
    • 序列号 (Sequence Number)： 从 1 开始递增，用来匹配发出去的包和收回来的包，顺便检查有没有丢包或乱序。
    • 时间戳 (Timestamp)： 记录发送这个包的精确时间，用来后续计算延迟（RTT）。
    • 数据 (Data)： 填充一些无意义的字节（比如 abcde…），用来凑够包的大小。

第二步：封装进 IP 数据包 (网络层向下传递)

  1. ICMP 报文被交给了底层的 IP 协议。
  2. IP 协议给它套上一个 IP 头部 (IP Header)。
    • 源 IP：你自己的 IP 地址。
    • 目的 IP：192.168.1.100。
    • 协议类型字段 (Protocol)：填入 1，表示这个 IP 包的 payload（载荷）是 ICMP 报文。

第三步：MAC 地址解析与物理传输 (数据链路层及以下)

  1. 如果源主机不知道目的 IP 的 MAC 地址，它会先发送 ARP 请求 进行广播查找。
  2. 拿到目标 MAC 地址后，IP 数据包被进一步封装成以太网帧 (Ethernet Frame)，通过网卡转换成电信号/光信号发往网络。

第四步：目标主机接收与响应 (目标主机处理)

  1. 目标主机网卡收到信号，层层解包：以太网帧 -> IP 数据包。
  2. 目标主机的 IP 协议检查目标 IP 是自己，并且看到 Protocol 字段是 1，就知道这是一个 ICMP 报文，于是把它交给 ICMP 协议处理模块。
  3. ICMP 模块发现这是一个 Echo Request (Type 8)，它明白这是有人在 ping 自己。
  4. 关键动作： 目标主机立刻构建一个 ICMP Echo Reply (Type 0) 报文。它会把收到的 Request 里的标识符、序列号、时间戳和数据原封不动地复制到 Reply 报文里。
  5. 然后，同样经过 IP 层封装、以太网帧封装，将这个 Reply 报文发回给源主机。

第五步：源主机接收应答与计算结果 (回到起点)

  1. 源主机收到这个 IP 包，解包发现是 ICMP 报文，交给 ping 程序。
  2. ping 程序检查报文类型是 Echo Reply (Type 0)。
  3. 它提取出报文里的序列号，确认这是刚才自己发出去的那个包的回应。
  4. 计算延迟 (RTT)： ping 程序读取当前系统时间，减去报文里原样返回的发送时间戳，得出往返耗时（如 time=10ms）。
  5. 最后，将结果打印在终端上。

3. 补充说明：Ping 不通的常见原因（展现排障能力）

面试官有时候会追问：“如果 ping 不通，可能是什么原因？”

你可以按层次回答：

  • 物理层/链路层： 网线没插好、网卡坏了、ARP 解析失败（比如目标 IP 根本不存在）。
  • 网络层 (路由问题)： 没有配置默认网关，或者沿途的路由器不知道怎么把包转发到目标网段（找不到路由表项），此时会收到 Destination Host Unreachable (目标主机不可达)。
  • 安全策略 (防火墙/安全组)： 这是最常见的原因。目标主机正常运行，但它的防火墙（如 iptables、Windows 防火墙）或者云服务器的安全组，拦截了 ICMP Echo Request (Type 8) 报文。此时你 ping 它会提示 Request timed out (请求超时)，但这并不代表它的 TCP 服务（比如 80 端口的 Web 服务）不通。

大量出现 TIME_WAIT、CLOSE_WAIT 有哪些可能的原因，解决办法？

time-wait：

原因：

  1. 在一些 TPS/QPS 很高的 REST 服务中，如果使用的是短连接（即没有开启keep-alive），则很可能发生客户端端口被占满的情形。这是由于短时间内会创建大量TCP 连接，而在 TCP 四次挥手结束后，客户端的端口会处于 TIME_WAIT一段时间(2*MSL)，这期间端口不会被释放，从而导致端口被占满。这种情况下最好使用长连接。
  2. 大量的瞬时高并发请求。并发客户端数量暴涨时，连接创建 + 关闭频率会非常高；
  3. 系统内核参数未调优，默认内核 TCP 参数较保守，回收 TIME_WAIT 状态的连接比较慢；如：tcp_fin_timeout 时间太长，`tcp_tw_recycle 没有开启等。

解决方法：

  • 开启连接复用，启用长连接
  • 合理限流，多请求复用一个连接

close_wait:

原因：

  • 本质：服务端没有主动调用 close() 关闭 socket。

  • **资源未释放：**被动关闭方未释放与连接相关的资源（如文件描述符、Socket 等）。如，数据库连接、网络连接等未正确关闭。
  • 程序异常:在处理连接时发生异常，导致未执行关闭逻辑。如，未捕获的异常导致 finally 块中的 close() 方法未执行。

解决方法：

  • 在代码中显式调用 close() 方法关闭连接。
  • 使用 try-with-resources 或 finally 块确保连接被关闭。
  • 确保所有与连接相关的资源都被正确释放。
  • 调整操作系统的 TCP 参数，减少 CLOSE_WAIT 状态的持续时间。

TCP/IP 网络分层

TCP/IP 四层模型 是目前被广泛采用的一种模型,我们可以将 TCP / IP 模型看作是 OSI 七层模型的精简版本，由以下 4 层组成：

  1. 应用层
  2. 传输层
  3. 网络层
  4. 网络接口层

需要注意的是，我们并不能将 TCP/IP 四层模型 和 OSI 七层模型完全精确地匹配起来，不过可以简单将两者对应起来，如下图所示：

应用层

应用层位于传输层之上，主要提供两个终端设备上的应用程序之间信息交换的服务，它定义了信息交换的格式，消息会交给下一层传输层来传输。 我们把应用层交互的数据单元称为报文。

应用层协议定义了网络通信规则，对于不同的网络应用需要不同的应用层协议。在互联网中应用层协议很多，如支持 Web 应用的 HTTP 协议，支持电子邮件的 SMTP 协议等等。

传输层

传输层的主要任务就是负责向两台终端设备进程之间的通信提供通用的数据传输服务。 应用进程利用该服务传送应用层报文。“通用的”是指并不针对某一个特定的网络应用，而是多种应用可以使用同一个运输层服务。

网络层

网络层负责为分组交换网上的不同主机提供通信服务。 在发送数据时，网络层把运输层产生的报文段或用户数据报封装成分组和包进行传送。在 TCP/IP 体系结构中，由于网络层使用 IP 协议，因此分组也叫 IP 数据报，简称数据报。

网络接口层

我们可以把网络接口层看作是数据链路层和物理层的合体。

  1. 数据链路层(data link layer)通常简称为链路层（ 两台主机之间的数据传输，总是在一段一段的链路上传送的）。数据链路层的作用是将网络层交下来的 IP 数据报组装成帧，在两个相邻节点间的链路上传送帧。每一帧包括数据和必要的控制信息（如同步信息，地址信息，差错控制等）。
  2. 物理层的作用是实现相邻计算机节点之间比特流的透明传送，尽可能屏蔽掉具体传输介质和物理设备的差异

1.tcp与udp的区别

  • 是否面向连接：UDP 在传送数据之前不需要先建立连接。而 TCP 提供面向连接的服务，在传送数据之前必须先建立连接，数据传送结束后要释放连接。

  • 是否是可靠传输：远地主机在收到 UDP 报文后，不需要给出任何确认，并且不保证数据不丢失，不保证是否顺序到达。TCP 提供可靠的传输服务，TCP 在传递数据之前，会有三次握手来建立连接，而且在数据传递时，有确认、窗口、重传、拥塞控制机制。通过 TCP 连接传输的数据，无差错、不丢失、不重复、并且按序到达。

  • 是否有状态：这个和上面的“是否可靠传输”相对应。TCP 传输是有状态的，这个有状态说的是 TCP 会去记录自己发送消息的状态比如消息是否发送了、是否被接收了等等。为此 ，TCP 需要维持复杂的连接状态表。而 UDP 是无状态服务，简单来说就是不管发出去之后的事情了（这很渣男！）。

  • 传输效率：由于使用 TCP 进行传输的时候多了连接、确认、重传等机制，所以 TCP 的传输效率要比 UDP 低很多。

  • 传输形式：TCP 是面向字节流的，UDP 是面向报文的。

  • 首部开销：TCP 首部开销（20 ～ 60 字节）比 UDP 首部开销（8 字节）要大。

  • 是否提供广播或多播服务：TCP 只支持点对点通信，UDP 支持一对一、一对多、多对一、多对多；

1.建立连接的三次握手

建立一个 TCP 连接需要“三次握手”，缺一不可：

  • 一次握手:客户端发送带有 SYN（SEQ=x） 标志的数据包 -> 服务端，然后客户端进入 SYN_SEND 状态，等待服务端的确认；

  • 二次握手:服务端发送带有 SYN+ACK(SEQ=y,ACK=x+1) 标志的数据包 –> 客户端,然后服务端进入 SYN_RECV 状态；

  • 三次握手:客户端发送带有 ACK(ACK=y+1) 标志的数据包 –> 服务端，然后客户端和服务端都进入ESTABLISHED 状态，完成 TCP 三次握手。

2.为什么要三次握手

三次握手的目的是建立可靠的通信信道，说到通讯，简单来说就是数据的发送与接收，而三次握手最主要的目的就是双方确认自己与对方的发送与接收是正常的。

TCP可靠传输的精髓：TCP连接的一方A，由操作系统动态随机选取一个32位长的序列号(InitialSequenceNumber)，假设A的初始序列号为1000，以该序列号为原点，对自己将要发送的每个字节的数据进行编号，1001，1002，1003..，并把自己的初始序列号ISN告诉B，让B有一个思想准备，什么样编号的数据是合法的，什么编号是非法的，比如编号900就是非法的，同时B还可以对A每一个编号的字节数据进行确认。如果A收到B确认编号为2001，则意味着字节编号为1001-
2000，共1000个字节已经安全到达。

同理B也是类似的操作，假设B的初始序列号ISN为2000，以该序列号为原点，对自己将要发送的每个字节的数据进行编号，2001，2002，2003..，并把自已的初始序列号ISN告诉A，以便A可以确认B发送的每一个字节。如果B收到A确认编号为4001，则意味着字节编号为2001-4000，共2000个
字节已经安全到达。

四次握手过程

1.1 A发送同步信号sYN + A’s Initial sequence number

1.2 B确认收到A的同步信号，并记录A’sISN到本地，命名B’sACKsequence number

1.3 B发送同步信号sYN + B’s Initial sequence number

1.4 A确认收到B的同步信号，并记录B’sISN到本地，命名A’sACKsequence number

很显然1.2和1.3这两个步骤可以合并，只需要三次握手，可以提高连接的速度与效率。

二次握手的过程

2.1 A发送同步信号sYN + A’s Initial sequence number
2.2 B发送同步信号sYN + B’s Initial sequence number + B’s ACKsequence number

这里有个问题就是A和B就A的序列号达成了一致，这里是1000，但是B无法知道A是否已经接收到自己的同步信号，如果这个同步信号丢失了，A无法知道B的序列号。

其它问题

如果A发送给B的确认丢失了，会重传吗？ 不会，TCP不会为没有数据的ACK重传

  • 第一个包，即A发给B的SYN中途被丢，没有到达B，A会周期性超时重传，直到收到B的确认
  • 第二个包，即B发给A的SYN+ACK中途被丢，没有到达A，B会周期性超时重传，直到收到A的确认
  • 第三个包，即A发给B的ACK中途被丢，没有到达B，A发完ACK，单方面认为TCP为Established状态，而B显然认为TCP为Active状态：
    • 假定此时双方都没有数据发送，B会周期性超时重传，直到收到A的确认，收到之后B的TCP连接也为Established状态，双向可以发包。
    • 假定此时A有数据发送，B收到A的Data+ACK，自然会切换为established状态，并接受A的Data。
    • 假定B有数据发送，数据发送不了，会一直周期性超时重传SYN+ACK，直到收到A的确认才可以发送数据。

  • 序号机制：保证数据是按序、完整到达
  • 合理分片：tcp会按最大传输单元(MTU)合理分片，接收方会缓存未按序到达的数据，重新排序后交给应用层。

  • 超时重传：如果发送一直收不到应答，可能是发送数据丢失，也可能是应答丢失，发送方再等待一段时间之后都会进行重传。

一、 核心痛点：HTTP/2 解决了什么，又留下了什么？

  • HTTP/2 的巨大进步：引入了多路复用 (Multiplexing)，允许在一个 TCP 连接上并行传输多个请求/响应流。这解决了 HTTP/1.1 时代的应用层队头阻塞。
  • HTTP/2 的致命缺陷：它依然运行在 TCP 之上。
    • TCP 队头阻塞 (Head-of-Line Blocking)：TCP 是一个严格有序的协议。如果在一个 TCP 连接中，某个数据包（Packet）在网络中丢失了，那么即使后面所有的数据包都已到达，TCP 协议栈也会把它们都扣在缓冲区里，直到那个丢失的包被重传并成功接收。
    • 对 HTTP/2 的影响：在弱网（高丢包率）环境下，一个包的丢失会阻塞该 TCP 连接上的所有 HTTP 请求（即使这些请求的数据已经到了），多路复用的优势荡然无存。

二、 HTTP/3 的解决方案：QUIC 协议

为了彻底根除 TCP 的队头阻塞，HTTP/3 做了一个大胆的决定：放弃 TCP，改用 UDP。

但是 UDP 是不可靠的。所以，Google 在 UDP 之上重新实现了一套可靠传输协议，这就是 QUIC (Quick UDP Internet Connections)。

QUIC 协议的核心特性：

  1. 基于 UDP，无队头阻塞：
    • QUIC 实现了流（Stream）级别的多路复用。
    • 每个 HTTP 请求/响应都跑在自己独立的流上。
    • 如果流 A 的某个 UDP 包丢了，只会阻塞流 A，流 B 和 C 完全不受影响，可以继续被应用层读取。这彻底解决了 TCP 的队头阻塞问题。
  2. 更快的连接建立 (0-RTT)：
    • TCP + TLS：需要 2-3 个 RTT（往返时间）才能完成握手并开始传输数据。
    • QUIC：集成了 TLS 1.3，将传输层和安全层握手合并了。
      • 首次连接：只需要 1-RTT。
      • 再次连接：可以利用缓存，实现 0-RTT，直接发送数据。
  3. 连接迁移 (Connection Migration)：
    • TCP 的痛点：连接是基于四元组（源IP、源端口、目标IP、目标端口）识别的。当你手机从 Wi-Fi 切换到 4G 时，IP 地址变了，所有 TCP 连接都会断开，需要重连。
    • QUIC 的改进：连接是基于一个 64 位的 Connection ID 识别的。只要 Connection ID 不变，即使你的 IP 地址变了，QUIC 连接依然可以无缝地继续传输数据，不会中断。

TCP 滑动窗口机制

1. 什么是滑动窗口？

滑动窗口是TCP协议用来实现可靠传输和流量控制的核心机制。

如果TCP每发送一个数据包，都要等接收方回复一个确认（ACK）才发下一个，那效率就太低了（类似于寄一封信，必须等收到回信才寄第二封）。为了提高效率，TCP允许发送方在没有收到确认的情况下，连续发送多个数据包。

但能连续发多少呢？这就需要一个“窗口”来限制。滑动窗口本质上是操作系统在内存中开辟的一段缓冲区。

2. 窗口里的数据分为几类？

在发送方的眼里，数据被分为四类。你可以想象一个矩形的框（窗口）套在一条长长的数据队列上：

  1. 已发送且收到ACK的： 位于窗口左侧，已经安全送达，可以从缓冲区删除了。
  2. 【窗口内】已发送但未收到ACK的： 发出去了，还在路上，或者等对方确认中。
  3. 【窗口内】未发送但允许发送的： 对方有足够的空间接收，随时可以发。
  4. 未发送且不允许发送的： 位于窗口右侧，超出了对方的接收能力，现在不能发。

3. 它是如何“滑动”的？

  • 向右滑动： 当发送方收到了接收方发来的 ACK 确认报文（确认了第2类数据），窗口的左边界就会向右移动，把对应的第4类数据拉进窗口变成第3类（允许发送）。这就是“滑动”的过程。
  • 窗口收缩/扩大： 窗口的大小并不是固定的，它是根据接收方的处理能力动态调整的。

4. 滑动窗口与流量控制（Flow Control）

滑动窗口不仅仅是为了提高发送速度，更是为了保护接收方不被撑死。

  • 每次接收方向发送方回复 ACK 报文时，TCP头部里都有一个专门的字段叫 Window Size（接收窗口大小，简称 rwnd）。
  • 这个字段是在告诉发送方：“我现在内核缓冲区还有多大空余位置，你接下来最多只能发这么多数据给我”。
  • 发送方看到这个数字后，就会严格遵守，调整自己发送窗口的大小。
  • 零窗口（Zero Window）： 如果接收方的应用程序卡住了，一直不读取缓冲区的数据，缓冲区满了，它就会向发送方发送 Window Size = 0 的报文。发送方收到后，就会立刻停止发送数据，直到接收方主动通知窗口恢复。

1.Hash加密算法（MD5等）

Hash加密算法是一种将任意长度的消息压缩成固定长度散列值的算法。它的特点是快速、不可逆和安全。Hash加密算法被广泛用于[数字签名、数据完整性验证等信息安全领域。本文将介绍Hash加密算法的基本原理、常用算法和应用场景。

Hash加密算法通过将任意长度的消息输入到算法中，经过一系列计算得到一个固定长度的Hash值。Hash值可以看作是消息的指纹，具有唯一性和不可逆性。对于相同的消息，执行相同的Hash算法得到的Hash值是相同的，但即使是输入消息的微小变化也会导致Hash值的巨大变化。因此，Hash加密算法可以用于验证数据完整性和数字签名等场景。
2.Hash碰撞

碰撞能不能避免？答案是不能。碰撞是一定会出现的，因为输出的字节长度是固定的， String 的 hashCode() 输出是 4 字节整数，最多只有 4294967296 种输出， 但输入的数据长度是不固定的，有无数种输入。所以，哈希算法是把一个无限的输入 集合映射到一个有限的输出集合，必然会产生碰撞。 碰撞不可怕，我们担心的不是碰撞，而是碰撞的概率，因为碰撞概率的高低关系 到哈希算法的安全性。一个安全的哈希算法必须满足： 碰撞概率低； 不能猜测输出。 不能猜测输出是指：输入的任意一个 bit 的变化会造成输出完全不同，这样就很难从输出反推输入（只能依靠暴力穷举）。
3.应用场景

数据完整性验证

Hash加密算法可以用于验证数据的完整性。发送方对数据计算Hash值，并将其发送给接收方。接收方对接收到的数据计算Hash值，如果两个Hash值相同，则可以确认数据没有被篡改。这种应用场景在互联网数据传输中非常常见，例如网站提供下载的软件文件通常会提供md5或sha1校验值，让用户利用Hash算法验证文件的完整性。

数字签名

Hash加密算法可以用于数字签名，即对数字信息进行签名，让接收方确认发送方的身份和内容的确是由发送方所发出的。发送方对消息计算Hash值，并使用自己的私钥对Hash值进行加密，形成数字签名并发送给接收方。接收方对消息计算Hash值，并使用发送方的公钥对数字签名进行解密，得出Hash值并与接收到的Hash值进行比对。如果两个Hash值相同，则确认发送方的身份和消息的完整性，数字签名有效。

长连接？长连接的适用场景是什么？哪些场景不适合使用长连接，原因是什么？

1. 什么是长连接 (Keep-Alive)？

长连接，也叫持久连接 (Persistent Connection)。
它的核心思想是：在一个 TCP 连接上，连续传输多个 HTTP 请求/响应，而不是每次请求都重新握手建连。

  • HTTP 1.0：默认短连接。请求 -> 握手 -> 传输 -> 挥手。
  • HTTP 1.1：默认长连接。请求 1 -> 握手 -> 传输 1 -> 传输 2 -> 传输 3 … -> 超时/挥手。

2. 适用场景是什么？

一句话总结：频繁交互、对延迟敏感的场景。

  1. 网页浏览（最典型）：
    • 一个网页通常包含几十个资源（HTML, CSS, JS, 图片）。
    • 如果不复用连接，加载一个网页要握手几十次，用户体验极差。
  2. API 频繁调用（微服务内部）：
    • Service A 频繁调用 Service B。如果不复用连接，CPU 会浪费在建立 TCP 和 SSL 握手及资源回收上。
  3. 数据库连接：
    • 数据库连接池就是典型的长连接应用。因为数据库认证过程非常慢。
  4. 即时通讯 (IM) / 推送：
    • WebSocket、MQTT。需要服务器能随时主动推数据给客户端，必须保持连接不断。

3. 哪些场景不适合？原因是什么？

一句话总结：客户端极多、并发极高、但单次请求很稀疏的场景。

  1. 超高并发的 Web 服务（如秒杀、门户首页）：
    • 原因：服务器的资源（文件句柄、内存、端口）是有限的。
    • 如果几百万用户都连着长连接不放，哪怕他们不发请求，服务器的连接数也会被占满，导致新用户连不进来（Nginx 报错“Too many open files”）。
    • 对策：这种场景下，服务端通常会把 keepalive_timeout 设得很短（如 2-5秒），或者直接让客户端发完就关，快速回收资源。
  2. 爬虫或定期任务：
    • 原因：爬虫爬完一个页面可能很久才爬下一个，或者根本不再来了。维持长连接纯属浪费服务器资源。
  3. DNS 查询：
    • 原因：DNS 通常基于 UDP（无连接），即使是 TCP DNS，也是查完就走，没必要保持。

RPC 和 HTTP 的区别

1. 协议体积与传输效率 (性能)

  • HTTP (RESTful)：
    • 太重了。HTTP 是一个非常臃肿的文本协议。即使你只传一个 id=1，它也要带上长长的请求头（Headers），如 User-Agent, Accept, Content-Type, 空行等。
    • 载荷比低：有效数据（Body）占整个数据包的比例很小。
  • 专有 RPC (如 Dubbo)：
    • 极度轻量。通常在 TCP 之上自定义二进制协议，头部信息极其精简（可能只有几个字节，用来标识消息长度、序列化类型等）。
    • 网络开销小：传输的数据量远小于 HTTP，在极高并发下，这能节省大量的带宽和网络 I/O 时间。

2. 序列化方式 (编解码)

  • HTTP (RESTful)：
    • 绝大多数使用 JSON 作为数据格式。
    • 缺点：JSON 是文本格式，体积大，且序列化/反序列化（解析字符串）的过程非常消耗 CPU。
  • 专有 RPC：
    • 通常支持高效的二进制序列化协议，如 Protobuf, Hessian, Kryo。
    • 优点：转成的二进制串体积极小，且编解码速度比 JSON 快几个数量级。

3. 开发体验与契约 (API 契约)

  • HTTP (RESTful)：
    • 缺乏强契约。你需要看 API 文档（如 Swagger），手写 HTTP 请求（拼 URL，设 Header），然后手动将返回的 JSON 解析成对象。
    • 即使有 OpenFeign，也需要写一堆 @RequestMapping 等注解。
  • 专有 RPC：
    • 面向接口编程。服务端提供一个 Interface 的 jar 包，客户端引入后，直接像调本地方法一样调：User user = userService.getUser(1);。
    • 底层复杂的网络通信、序列化都被框架（Stub / Proxy）透明地屏蔽了。

Springboot接受到请求后，网络模型是怎么走的？请求是怎么处理的？谁接收请求？事务怎么处理？NOI模型？

第一阶段：网络层与服务器层（谁接收请求？NIO 模型是怎么走的？）

结论先行：Spring Boot 本身并不直接监听网络端口和接收 TCP 请求。这个活儿是由它内置的 Web 服务器（默认是 Tomcat）干的。

Tomcat 默认采用的是 NIO 通信模型（基于 Reactor 模式），整个接收过程分为三大组件协同工作：

  1. Acceptor（接收者线程，通常 1-2 个）：
    • 职责： 它是“大堂门迎”。它只负责监听 8080 端口，当客户端发起 TCP 三次握手成功后，它会接收这个连接（SocketChannel），然后迅速把这个连接转交给 Poller，自己立马回去继续接客。
  2. Poller（轮询者线程，通常 1-2 个）：
    • 职责： 它是“大堂经理”。这就是 NIO 模型的精髓所在。它底层使用了操作系统的多路复用技术（Linux 下是 epoll）。
    • NIO 的体现： Poller 会在一个死循环中，利用 Selector 同时监控成千上万个连接（Channel）。它不会阻塞等待某个连接发数据，而是只有当某个连接真正有数据到达（比如 HTTP 请求的字节流发过来了），epoll 才会通知 Poller：这根网线有数据了，去处理吧！
  3. Worker 线程池（打工人线程，默认最大 200 个）：
    • 职责： 它是“业务员”。当 Poller 发现某个连接有数据可读时，它会把读取数据的任务包装成一个任务，扔给 Worker 线程池。
    • 关键动作： 一个空闲的 Worker 线程被唤醒，它负责将网络传来的二进制字节流，按照 HTTP 协议规范，解析、组装成 Java 语言认识的 HttpServletRequest 和 HttpServletResponse 对象。

至此，网络模型的使命结束，Tomcat 的 Worker 线程端着封装好的 Request 对象，正式踏入 Spring 的大门。

第二阶段：框架层（请求是怎么处理的？）

在这个阶段，一切操作都发生在上一步分配的那个特定的 Tomcat Worker 线程中。

请求处理的核心枢纽是 Spring MVC 的绝对核心：DispatcherServlet（前端控制器）。它的 doDispatch() 方法是整个流程的心脏。

  1. Filter 链过滤：
    请求到达 Servlet 之前，会先穿过一系列的 Filter（过滤器）。比如做字符编码转换的 CharacterEncodingFilter，以及极其重要的做安全校验的 Spring Security Filter Chain。
  2. 寻找 Handler (处理器映射)：
    进入 DispatcherServlet 后，它会调用 HandlerMapping。根据请求的 URL（比如 /api/user/1）和 Method（GET），去内部的注册表里查找，看看是由哪个 @RestController 里的哪个方法来处理。查到后，返回一个包含了目标方法和所有拦截器的执行链（HandlerExecutionChain）。
  3. 执行拦截器 (Interceptor)：
    在真正执行 Controller 之前，会按顺序执行配置的 HandlerInterceptor 的 preHandle 方法（常用于做鉴权、日志、限流）。如果某个拦截器返回 false，请求直接被打回。
  4. 参数解析与执行 (HandlerAdapter)：
    这是最脏最累的活。DispatcherServlet 找到合适的 HandlerAdapter 去执行 Controller 方法。
    • 它会利用 HttpMessageConverter（默认是 Jackson），将 HTTP 请求体里的 JSON 字符串反序列化为你 Controller 方法里的 @RequestBody UserDTO 对象。
  5. 进入 Controller 业务逻辑：
    此时，终于真正进入了你写的代码：Controller -> Service -> DAO。
  6. 结果返回与序列化：
    Controller 方法执行完毕返回一个对象（如 User），HandlerAdapter 再次利用 Jackson，将这个 Java 对象序列化成 JSON 字符串，写入 HttpServletResponse 中，原路返回给 Tomcat，Tomcat 再通过网络发给客户端。

第三阶段：业务与数据层（事务怎么处理的？）

当请求走到 Service 层，遇到了 @Transactional 注解时，事务机制开始发挥作用。

事务处理的底层原理是：AOP（动态代理） + ThreadLocal。

  1. 代理对象的介入 (AOP)：
    Spring IOC 容器在启动时，发现你的 UserService 类上有 @Transactional 注解，它就不会把真实的 UserService 注入给 Controller，而是利用 CGLIB（或 JDK 动态代理）生成一个代理类注入进去。
  2. 开启事务 (TransactionInterceptor)：
    当 Controller 调用 userService.createUser() 时，实际上调用的是代理类。代理类内部的事务拦截器会被触发：
    • 它向数据库连接池（如 HikariCP）申请一个空闲的数据库连接（Connection）。
    • 极其关键的一步： 它将 connection.setAutoCommit(false)，关闭自动提交，正式开启物理事务。
  3. ThreadLocal 绑定（保证同一个事务）：
    开启事务后，Spring 会将这个具体的 Connection 对象，绑定到当前的线程上（即第一阶段分配的那个 Tomcat Worker 线程），使用的工具就是 ThreadLocal。
    • 为什么这么做？ 因为这样一来，你在 createUser 方法内部调用的无论多少个 Mapper/DAO 操作，MyBatis 在底层获取连接时，都会从当前线程的 ThreadLocal 里去拿。大家拿到的是同一个 Connection，自然就在同一个数据库事务里了。
  4. 执行业务与异常捕获：
    代理类通过反射调用你真实的 createUser 业务代码。
  5. 提交或回滚 (Commit / Rollback)：
    • 成功： 如果真实方法顺利执行完毕，没有抛出任何异常，事务拦截器会调用 connection.commit()，将数据永久写入数据库。
    • 失败： 如果真实方法抛出了异常（默认情况下是 RuntimeException 或 Error），事务拦截器会捕获到，并调用 connection.rollback()，撤销所有操作。
  6. 清理现场：
    无论成功还是失败，最后事务拦截器都会将 Connection 恢复为自动提交状态，将其归还给连接池，并且极其重要地，从 ThreadLocal 中清除该连接（防止线程复用导致内存泄漏和事务错乱）。

  2. 数字签名 (Digital Signature)：

HTTPS 是对称加密吗，为什么用对称密钥而不是更安全的非对称加密？

  1. 性能极差（致命伤）：
    • 非对称加密（如 RSA, ECC）的数学原理极其复杂（基于大数分解或椭圆曲线），它的加密和解密速度比对称加密（如 AES, ChaCha20）慢几个数量级（通常慢 100 到 1000 倍以上）。
    • 如果用非对称加密来传输几 MB 的图片或视频流，服务器的 CPU 瞬间就会被打满，客户端也会卡死，现有的互联网速度根本无法承受。
  2. 只能单向安全通信：
    • 非对称加密有一对密钥：公钥和私钥。公钥是公开的（任何人都能拿到服务器的证书），私钥只有服务器自己有。
    • 客户端到服务器： 客户端用公钥加密数据，只有服务器能用私钥解密，这是安全的。
    • 服务器到客户端： 如果服务器用私钥加密响应数据发给客户端，因为公钥是全网公开的，任何中间人（黑客）都能用公钥解密看到内容，这毫无保密性可言。

TCP 如何判断报文丢失，什么条件触发重传?TCP 除重传计时器外还有哪些计时器

TCP 并没有一种直接的物理方式去“看到”报文在网络中丢失了，它完全依赖于接收方的确认（ACK）机制来间接推断报文是否丢失。

TCP 触发重传主要有两种条件：超时重传 和 快速重传。

条件 1：超时触发（超时重传 Timeout Retransmission）

  • 判断依据： 时间到了，还没收到确认。
  • 工作机制：
    1. TCP 发送方在发送一个报文段时，会启动一个重传计时器（Retransmission Timer）。
    2. 这个计时器的时间被设定为 RTO（Retransmission Timeout，重传超时时间）。RTO 并不是固定的，而是根据网络的实时往返时间（RTT）动态计算出来的。
    3. 如果在 RTO 规定的时间内，发送方没有收到该报文段的 ACK 确认（可能是报文丢了，也可能是 ACK 丢了，或者网络严重拥塞延迟了），TCP 就会判断该报文丢失。
  • 触发动作： 计时器超时，自动重新发送该报文段。

条件 2：收到 3 次重复确认触发（快速重传 Fast Retransmit）

  • 判断依据： 收到连续相同的确认序号，说明某个报文没按序到达。
  • 工作机制：
    1. TCP 接收方在收到失序的报文时，不会对那个失序的报文发送确认，而是立即发送对前一个按序到达报文的重复确认（Duplicate ACK）。
    2. 比如：发送方发送了序号为 1, 2, 3, 4, 5 的报文。报文 2 在网络中丢失了，而 3, 4, 5 成功到达。接收方收到 3 时，会发送对报文 1 的确认（意思是“我期望收到 2”）；收到 4 时，又发送对 1 的确认；收到 5 时，依然发送对 1 的确认。
  • 触发动作： 当发送方收到连续 3 个重复的 ACK（加上原本正常的那个，总共 4 个相同的 ACK）时，它就会确信报文 2 已经丢失，不等重传计时器超时，立即重传报文 2。这被称为快速重传。

2. 时间等待计时器 (Time-Wait Timer / 2MSL 计时器)

  • 解决的问题： 确保连接安全关闭，防止旧报文干扰新连接。
  • 触发场景： 发生在 TCP 四次挥手断开连接的最后阶段。主动关闭连接的一方（通常是客户端）在发送完最后一个 ACK 后，会进入 TIME_WAIT 状态，并启动这个计时器。
  • 工作机制： 计时器的时长通常设置为 2MSL（Maximum Segment Lifetime 的两倍，通常为 1~4 分钟）。在这段时间内，连接并未彻底释放。
  • 目的：
    1. 确保最后一个 ACK 能到达对方。如果 ACK 丢失，对方会重发 FIN，主动关闭方在这段时间内还能响应重传 ACK。
    2. 让网络中残留的、延迟的“旧报文”在网络中自然消亡，防止它们在相同端口建立新连接后，被错误地当成新连接的数据接收。

3. 保活计时器 (Keepalive Timer)

  • 解决的问题： 清理“死连接”，防止资源浪费。
  • 触发场景： 客户端和服务器建立了连接，但由于客户端突然断电、网线拔出等物理故障，没来得及发送断开请求（FIN），导致服务器一直维持着这个空闲的连接。
  • 工作机制： 服务器每收到一次客户端的数据，就会重置保活计时器（通常默认是 2 小时）。如果 2 小时内没有任何数据交换，服务器就会发送一个探测报文（Keepalive Probe）。
  • 动作： 如果发送多次探测报文（通常是 9 次，每次间隔 75 秒）都没有收到客户端的响应，服务器就会判定客户端出故障，从而强制关闭这个连接，释放系统资源。

Oauth2的不同角色

OAuth 2.0 的四个核心角色

1. 资源所有者 (Resource Owner)

  • 大白话解释： 数据的真正主人，通常就是**“用户”（你）**。
  • 它的权力： 它有权决定是否把自己的数据（资源）授权给别人访问。
  • 场景代入： 你。你拥有自己在微信里的“头像”、“昵称”和“地区”等信息的所有权。当你点击“同意授权”时，就是作为资源所有者在行使权力。

2. 客户端 (Client)

  • 大白话解释： 想要访问用户数据的第三方应用程序（Web 网站、手机 App 或桌面软件）。
  • 它的诉求： 它本身没有用户的数据，它需要代替用户去获取数据，以便为你提供服务。（注意：这里的“Client”不是指用户的浏览器，而是指第三方应用背后的服务器或 App 本体）。
  • 场景代入： 哔哩哔哩 (B站)。B站想获取你的微信头像和昵称来帮你创建B站账号，所以B站就是这里的“客户端”。

3. 授权服务器 (Authorization Server)

  • 大白话解释： 负责“验明正身”并“颁发通行证”的安保中心。
  • 它的职责：
    1. 验证资源所有者（用户）的身份（比如让你扫码或输入密码）。
    2. 询问用户是否同意授权给客户端。
    3. 如果用户同意，它就给客户端颁发一个 Access Token（访问令牌）。
  • 场景代入： 微信的登录/授权服务器。当你在B站点击“微信登录”时，弹出的那个带有微信绿色按钮、让你扫码或点击“同意”的页面，背后就是微信的授权服务器在工作。

4. 资源服务器 (Resource Server)

  • 大白话解释： 真正存放用户数据的数据仓库。

  • 它的职责： 它只认“令牌（Token）”不认人。它接收客户端发来的 Access Token，验证 Token 的有效性和权限范围（Scope），如果合法，就把数据返回给客户端。

  • 场景代入： 微信的开放 API 服务器。它存储了你的头像图片和昵称字符串。B站拿到 Token 后，会带着这个 Token 去请求这个服务器，把你的头像拉取回B站。

  1. 授权服务器与资源服务器的关系：
    • 在逻辑上，它们是完全独立的两个角色（一个是发证的，一个是验证给东西的）。
    • 但在实际物理部署中，它们通常属于同一家公司，甚至可能部署在同一个服务端应用里。比如微信的授权服务器和 API 服务器都是腾讯在维护。但在大型微服务架构中（如 Google），它们往往是分离的分布式系统。

HTTP 协议的数据压缩主要是通过客户端和服务端之间的“内容协商（Content Negotiation）”机制来实现的。这个过程完全依赖于 HTTP Header。

  1. 客户端声明支持的算法 (Request)：
    当浏览器（客户端）发起 HTTP 请求时，它会在请求头中带上 Accept-Encoding 字段，告诉服务器自己能够解压哪些算法。
    • 例如：Accept-Encoding: gzip, deflate, br, zstd。这就表示客户端支持这四种主流的压缩算法。
  2. 服务端选择并压缩数据 (Response)：
    服务器收到请求后，会检查客户端发来的 Accept-Encoding 列表。
    • 如果服务器也支持其中的某种算法（通常会选择压缩率最高或最省 CPU 的一种），它就会在返回数据之前，使用该算法对响应体（Body）进行压缩。
    • 然后，服务器在响应头中带上 Content-Encoding 字段，明确告诉客户端：“我最终使用了哪种算法压缩了数据”。
    • 例如：Content-Encoding: gzip。
  3. 客户端解压缩 (Rendering)：
    客户端收到响应后，看到 Content-Encoding: gzip，就会调用相应的 gzip 解压模块，将 Body 还原成原始的 HTML、CSS 或 JSON 数据，最后进行渲染或处理。
