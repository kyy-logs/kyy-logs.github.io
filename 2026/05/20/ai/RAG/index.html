RAG和传统搜索有什么区别？

工作流程 (Workflow)

  • 传统搜索 (如 Google, Elasticsearch):

    1. 关键词匹配： 你输入“RAG 和传统搜索的区别”，它会用倒排索引等技术，找出包含这些关键词的文档。
    2. 排序： 使用 PageRank、BM25 等算法，对找到的文档进行相关性排序。
    3. 返回列表： 将排序后的文档链接列表直接呈现给你。
    • 核心： 信息检索 (Information Retrieval)。

  • RAG (检索增强生成):

    1. 【检索阶段 - Retrieval】(类似传统搜索，但目标不同):
      • 你输入同样的问题。系统先将你的问题向量化。
      • 去向量数据库中，寻找与你问题向量最相似的文本块（Chunks）。这一步的目标不是给你看，而是找“原材料”。
    2. 【增强阶段 - Augmentation】:
      • 系统将你原始的问题和检索到的原材料文本，通过一个 Prompt 模板，拼接成一个新的、更丰富的 Prompt。
      • 示例 Prompt: “你是一个专家，请根据以下背景知识：[‘检索到的文本块1’, ‘文本块2’]，来回答这个问题：’RAG 和传统搜索的区别是什么？’”
    3. 【生成阶段 - Generation】:
      • 将这个增强后的 Prompt 发送给大语言模型（大模型）。
      • 大模型阅读并理解你提供的背景知识，然后用自己的语言组织并生成一个直接、连贯的答案。
    • 核心： 检索 + 理解 + 生成 (Retrieval + Comprehension + Generation)。

  • 传统搜索：

    • 优势： 速度极快，信息保真度高（因为是原文），适合需要广泛浏览和自主研究的场景。
    • 场景： 查找特定文档、网页、商品。

  • RAG：

    • 优势：
      • 减少幻觉： 大模型的回答被限制在提供的“原材料”范围内，不会凭空捏造。
      • 知识更新： 可以通过更新向量数据库，让大模型掌握最新的、私有的知识，而无需重新训练模型。
      • 提供溯源： 可以展示答案是根据哪些原始文本块生成的，增加了可信度。
    • 场景： 企业内部知识库问答、智能客服、财报分析、代码解释等需要基于特定知识进行问答的场景。

“关键词召回依靠倒排索引，适合编号、专有名词等需要绝对精准匹配的场景，它的下限很高且可解释性强；而语义召回依靠向量距离，适合口语化长句、需要同义推断和意图理解的场景，能极大地缓解词汇鸿沟问题。

在我设计架构时，绝不会二选一，而是采用混合召回（Hybrid Search）。通过倒排索引保证精准度的底线，通过向量检索提升长尾 Query 的召回率，最后辅以 RRF 或 Reranker 模型进行融合排序，这样才能应对真实的复杂业务需求。”

项目中的上下文工程如何做的？这个从哪些角度回答呢(agent角色+动态RAG+TOOLS+记忆+运行上下文)

角度一：静态上下文（Static Context）—— 定义 Agent 的“灵魂”和“边界”

这是 Agent 的“出厂设置”，相对固定，决定了它的身份、能力和行为准则。

  • 1. Agent Persona & Role（角色与人设）：
    • 在我的 SOP 架构中，每个 Agent（分析、执行、监督、总结）都有自己独立的、精心设计的 System Prompt。比如“监督 Agent”的人设就是“一个追求极致代码质量的高级架构师”，这能极大提升它的批判性思维。
  • 2. Global Instructions & Guardrails（全局指令与护栏）：
    • 这里定义了整个任务的最终目标、输出格式的强制要求（如必须返回 JSON）、以及安全护栏（如“严禁透露个人隐私”、“严禁执行删除数据库等高危操作”）。这是保证 Agent 不“越狱”的第一道防线。

角度二：动态上下文（Dynamic Context）—— 为 Agent 注入“实时知识”和“世界交互能力”

这是上下文工程的重中之重，它让 Agent 从一个“离线书呆子”变成一个能连接真实世界的“实干家”。这部分信息是按需检索、动态注入的。

  • 1. 外部知识（RAG - 检索增强生成）：
    • 当 Agent 需要回答其训练数据中没有的私有领域知识时，系统会先根据用户问题，去向量数据库中检索最相关的知识片段（Chunks），然后将这些片段作为上下文注入。
    • 工程细节（体现深度）：我们不只是简单检索。在工程上，我们做了**元数据过滤（Metadata Filtering）**来保证多租户数据隔离；还做了**重排序（Re-ranking）**，确保最关键的知识片段放在上下文的最前面，避免 LLM 的“中间遗忘（Lost in the middle）”问题。
  • 2. 外部能力（Tools/MCPs）：
    • 这是解决 Tools 过多 问题的关键。我不会把上百个工具的 Schema 全都塞进去。在我的架构中，采用了基于 RAG 的工具动态检索（Tool Retrieval）。系统会先把用户的意图去一个专门的“工具向量库”里检索，只找出最相关的 3-5 个工具的定义，动态地注入到上下文中。

角度三：会话上下文（Conversational Context）—— 赋予 Agent “记忆”

这部分解决了大模型无状态的问题，让 Agent 能够理解多轮对话的来龙去脉。

  • 1. 短期记忆（Short-term Memory）：
    • 我们使用 Redis 存储每个 Session_ID 下的对话历史。但为了防止 Token 溢出，我们采用了**滑动窗口 + 摘要（Sliding Window with Summarization）**的策略。系统只保留最近 K 轮的完整对话，更早的对话会被另一个 LLM 调用（或本地模型）自动总结成一段摘要，极大压缩了 Token 占用。
  • 2. 长期记忆（Long-term Memory）：
    • 在每次 SOP 流程结束后，“总结 Agent”会提取本次交互中关于用户的关键信息（如偏好、身份），将其向量化并存入一个专门的**“用户画像向量库”**。下次用户再来时，系统会优先检索这份长期记忆，让 Agent 表现得更懂用户。

RAG如何进行数据预处理，LLM最终看到的块是什么格式的

一、 RAG 数据预处理的 4 步标准流程

无论你的源数据是 PDF、Word、HTML 还是数据库，预处理通常遵循以下严格的四个步骤：

1. 数据解析与清洗（Parsing & Cleaning）

这是最脏最累的活。

  • 提取内容：把非结构化数据（如 PDF 里的表格、图片、双栏排版文字）提取为纯文本。
    • 进阶做法：对于复杂的 PDF，工业界通常使用 OCR（如 PaddleOCR）配合版面分析（Layout Analysis）模型，识别出标题、正文、页眉、页脚。
  • 清洗去噪：剔除毫无意义的信息。
    • 删除多余的换行符、空格。
    • 删除页眉、页脚、版权声明（这些东西如果被检索出来喂给 LLM，纯属浪费 Token）。
    • 修复乱码或特殊符号。

2. 文档分块（Chunking / Splitting）—— 核心技术点

把清洗后的大长文，切成一段一段的文本块（Chunk），以便存入向量数据库并被精准检索。切法决定了 RAG 的生死。

  • 固定长度切分（按字数/Token数）：比如每 500 个 Token 切一刀。
    • 缺点：很容易把一句完整的话、或者一个完整的上下文语义从中间劈开，导致检索出来的 Chunk 词不达意。
  • 基于规则的切分（如 LangChain 的 RecursiveCharacterTextSplitter）：
    • 先尝试按段落（\n\n）切，如果段落还是太长，再按句子（。 或 .）切，最后再按字数切。这种方法尽量保证了句子的完整性。
  • 基于语义的切分（Semantic Chunking）—— 进阶高级玩法：
    • 通过自然语言处理模型，识别出文本中“主题发生切换”的位置，在主题切换处切分。确保每个 Chunk 讲的是同一个核心意思。
  • 重叠（Overlap）：无论怎么切，相邻的两个 Chunk 之间必须有一段重叠（比如重叠 100 个 Token）。这样能防止关键信息正好被切断在两个块的边界处。

3. 向量化（Embedding）

将切好的文本块（Chunk）输入给 Embedding 模型（如 OpenAI 的 text-embedding-3-small 或开源的 bge-m3），将人类能看懂的文字转换成机器能理解的多维浮点数数组（向量）。

4. 元数据注入（Metadata Enrichment）—— 极其重要！

这是区分“玩具 RAG”和“企业级 RAG”的分水岭。
在把 Chunk 和它的向量存入向量数据库（如 Milvus、Qdrant）时，绝对不能只存一段干瘪的文本，必须附带丰富的元数据（字典/JSON）。

  • 比如：{“doc_id”: “123”, “title”: “2024年员工手册”, “author”: “HR部”, “timestamp”: “2024-01-01”, “chunk_index”: 5, “access_level”: “public”}
  • 用途：未来在检索时，可以先通过这些元数据进行硬过滤（Metadata Filtering），比如“只检索 HR 部在 2024 年发的公开文档”，然后再进行向量相似度计算，极大提升准确率。

关于问题 4：“Rerank 后返回几个块？”

“在我们搭建的 RAG 系统中，Rerank 后最终送给大模型的 Chunk 数量（Top-K）是一个经过严格实验验证的权衡结果，通常我们设定在 3 到 5 个之间。

我们之所以不选择更多，是为了规避两个核心风险：

  1. 大模型的‘迷失在中间’（Lost in the Middle）效应： 学术界和我们自己的实验都证明，当上下文过长时，大模型的注意力会集中在开头和结尾，导致中间的关键信息被忽略，准确率不升反降。
  2. 成本与延迟： 过多的 Chunk 会显著增加 Token 消耗和 API 响应时间，影响用户体验和运营成本。

我们也不选择更少，比如只返回 Top-1，是因为对于复杂问题，答案往往分散在多个文档片段中，只给一个会导致信息不全，无法生成全面、准确的答案。

这个 3-5 的值是我们通过自动化评测流水线得出的。 我们构建了一个包含数百个业务问题的‘黄金标准集’，然后通过网格搜索（Grid Search）测试了不同的 Top-K 值，并重点监控了三个自动化评测指标：Answer Relevance（答案相关性）、Faithfulness（忠实度/无幻觉率）和 Context Precision（上下文精确度）。实验结果显示，当 K 超过 5 时，相关性收益基本见顶，但上下文噪声和幻觉率开始明显上升，因此 3-5 是我们当前业务场景下的最佳平衡点。”

关于问题 5：“Rerank 后的 TopK 截断是怎么做的？”

“对于 Rerank 后的结果截断，我们绝对不使用僵硬的‘固定 Top-K 硬截断’，因为这在面对知识库中不存在答案的场景时，会强行喂给大模型一堆不相关的垃圾上下文，导致严重的幻觉。

我们的截断策略是一个**‘动态漏斗组合’**：

  1. 第一层：绝对分数阈值（Absolute Score Threshold）
    • 这是我们最核心的防御机制。我们的 Reranker 模型（交叉编码器）能输出 0-1 之间的绝对相关性分数。我们通过离线评测找到了一个最佳的置信度阈值（比如 0.45）。任何 Rerank 分数低于这个阈值的 Chunk，无论排名多高，都会被直接抛弃。
    • 这个机制的最大好处是： 如果所有 Chunk 都被抛弃，说明知识库里很可能就没有答案。我们的 Agent 此时会触发安全降级逻辑，直接告诉用户‘找不到相关信息’，彻底杜绝了基于垃圾上下文的胡编乱造。
  2. 第二层：最大数量上限（Max-K Cap）
    • 在通过了分数阈值之后，我们再设定一个最大数量上限（比如 K=5），这是为了防止过多高质量 Chunk 导致‘迷失在中间’。
  3. （可选的高级策略）第三层：相对分数跌落（Relative Score Drop）
    • 我们还会观察分数列表的梯度。如果出现从 0.9 突然暴跌到 0.2 这样的断崖，我们会智能地在断崖处提前截断，确保送给大模型的上下文都是同一高质量梯队的。

  1. 关于切分策略：我采用的是**‘结构感知 + 递归兜底’的混合策略**。我会优先利用 Markdown 或版面分析模型，按真实的文档章节（如 # 标题）进行切块。只有在结构层级不明显时，才会降级使用按段落、句号切分的语义递归策略。
  2. 面对极端长度的段落：我会设置一个动态的滑动窗口（比如 Min=300, Max=800）。对于 100 字的短段落，我会执行‘向上聚合’，把它和相邻段落拼接，避免上下文太短导致向量特征模糊（所谓的碎片化噪音）；对于 1 万字的长段落，我会执行‘向下递归切分’，逐级按句号、逗号甚至字符强制斩断，确保没有任何一个块超过 Embedding 模型的上限。
  3. 关于 Chunk Size 的设定依据：我们定在 500 到 800 Token 之间。这并非主观猜测，而是基于三个维度的权衡：第一是适配底层 Embedding 模型（如 BGE-Large）的最佳输入长度；第二是考虑 LLM 的上下文预算（如果召回 Top-5，加起来不能撑爆窗口）；第三，也是最核心的，我们通过 RAGAS 评估框架跑过真实的 Ground Truth 测试集，对比了 300、500、1000 三个粒度，发现 500-800 之间的召回命中率（Hit Rate）和 MRR 得分最高。
  4. 关于 Overlap 的设定：我将其固定在 100 个 Token 左右（约占 15%）。这么做是为了解决**‘共指消解’和‘上下文断裂’**问题。100 个 Token 刚好能覆盖中文 2 到 3 个句子的跨度，足以确保上一段末尾的主语（比如‘张三’）能够平滑地延伸到下一段的开头（比如‘他指出…’），防止 LLM 在生成答案时张冠李戴。

向量检索和 BM25 的融合比例是怎样的？

“在我们的混合检索（Hybrid Search）架构中，关于向量检索和 BM25 的融合比例，我没有采用拍脑袋的固定值，而是基于一套**‘场景分类 + 归一化 + 网格搜索评估’**的工程化体系来落地的。

首先，在底层算法上，我没有直接使用原始分数相加。因为 BM25 的得分是无界的，而向量的余弦相似度是有界的。我先对两者做了Min-Max 归一化（Normalization），然后再引入参数 Alpha 进行线性加权。(注：如果你们用的是 RRF，这里可以说：为了避免分数尺度不一致的问题，我直接采用了基于排名的 RRF 倒数排名融合算法，绕过了绝对分数的权重分配。)

其次，关于具体比例的设定，这是由业务的数据特征决定的：
对于包含大量专有名词、订单号、错误代码的业务线（比如运维排障），我将 Alpha 调低，把 BM25 的权重拉到了 0.7 左右，确保精准匹配不被语义泛化吃掉；
而对于泛知识库问答场景，用户提问极其口语化，我将 向量检索的权重拉高到了 0.8，用以弥补关键字匹配不到的语义鸿沟。

最后，这个比例不是一成不变的。我们会构建一个真实的 Ground Truth 评测数据集（包含 1000 个真实 Query 和标准答案文档）。然后利用自动化脚本进行网格搜索（Grid Search），让 Alpha 从 0.1 步进到 0.9，跑出每一组权重下的 NDCG@10 和召回命中率（Hit Rate）。数据指标跑到哪里最高，我们线上的融合比例就设为多少。”

大模型幻觉产生的原因？RAG幻觉如何处理？

大模型幻觉（Hallucination）产生的原因？

大模型“一本正经地胡说八道”，本质上是因为大模型是基于概率预测下一个Token的统计模型，而不是确定的知识数据库。

  • 数据层面：训练数据中包含过时信息、错误知识、相互矛盾的内容，或者模型根本没见过相关数据。
  • 原理层面：模型缺乏真实的逻辑推理能力，它只是在寻找上下文中概率最高的词进行拼接，当上下文不足时，它倾向于“编造”合理的连缀。
  • 对齐税 (Alignment Tax)：在 RLHF（强化学习人类反馈）微调阶段，如果过度鼓励模型回答问题（而不是承认不知道），模型就会倾向于生成看似合理但实际错误的答案以取悦人类。
  • 上下文过长：在处理超长文本时，模型容易出现“迷失在中间（Lost in the middle）”的现象，忽略或混淆了关键信息。

一、 检索环节出问题（“找错了” 或 “没找到”）

这是 RAG 幻觉最常见的来源。大模型就像一个极其聪明的考生，但如果开卷考试给的参考资料是错的、碎的、或者无关的（Garbage In），它产出的答案必然是错的（Garbage Out）。

1. 知识库本身质量差（源头污染）

  • 原因：你喂给向量数据库的文档本身就包含过期的、自相矛盾的、或者错误的知识。
  • 结果：大模型非常“忠实”地提取了这些错误信息，这在用户看来就是幻觉，但实际上是系统“如实转述”了错误。

2. 分块（Chunking）策略不当导致语义割裂

  • 原因：文档被生硬地按固定字数切分。比如一句话“不建议在孕期使用该药物”，被切成了两块：块A是“不”，块B是“建议在孕期使用该药物”。
  • 结果：如果检索只召回了块B，大模型就会给出完全相反的致命错误答案。缺失上下文是导致事实扭曲的重灾区。

3. 语义检索的局限性（匹配偏差）

  • 原因：Embedding 模型在理解复杂意图、特定缩写或细微逻辑关系时能力不足。比如搜索“苹果公司的负面新闻”，模型可能召回了大量关于“苹果营养价值”或“苹果公司正面财报”的文档，因为它们在向量空间里都很接近。
  • 结果：大模型拿着一堆相关但不切题的文档，强行回答问题，从而产生捏造。

4. 召回噪音过多（Top-K 污染）

  • 原因：为了保证能找到答案，系统一次性召回了 Top 10 的文档片段。其中只有 1 段是正确答案，另外 9 段是相似但无关的噪音。
  • 结果：这些噪音信息会严重干扰大模型的判断，导致它把不同文档里的概念张冠李戴（例如把A公司的财报数据安到了B公司头上）。

二、 组装与理解环节出问题（“没看懂” 或 “看漏了”）

即使找回来的参考资料是正确的，大模型在阅读这些资料时也会出现“认知障碍”。

5. 迷失在中间（Lost in the Middle）现象

  • 原因：这是当前 LLM 的一个普遍缺陷。当给定的上下文（Context）非常长时，大模型通常只对开头和结尾的信息保持较高的注意力，而会忽略或遗忘中间部分的信息。
  • 结果：如果关键答案恰好位于召回片段的中间位置，大模型可能会视而不见，转而靠自己瞎猜。

阶段一：事前预防 —— 优化检索质量 (Garbage In, Garbage Out)

这是最重要、最根本的一步。如果送给 LLM 的上下文（Context）本身就是错误的、无关的或不完整的，那么再强的 LLM 也难免会产生幻觉。

1. 提升分块策略 (Chunking Strategy)

低质量的文本块是万恶之源。

  • 问题：简单的固定大小分块会割裂语义，导致上下文不完整。
  • 解决方案：
    • 语义分块 (Semantic Chunking)：使用模型（如Sentence-Transformers）根据语义的完整性来切分文档，保证每个块都是一个相对完整的意义单元。
    • 内容感知分块: 针对不同类型的内容（如Markdown表格、代码、段落）使用不同的分块逻辑。
    • 块重叠 (Chunk Overlap)：在块与块之间保留一部分重叠内容，确保在边界处的语义连续性。

2. 优化 Embedding 模型

  • 问题：通用的 Embedding 模型可能无法很好地理解你所在领域的专业术语。
  • 解决方案：
    • 使用领域专用模型: 选择在你的专业领域（如金融、医疗）预训练过的 Embedding 模型。
    • 微调 (Fine-tuning)：在你自己的数据集上对 Embedding 模型进行微调，让它更懂你的业务语言。

3. 采用混合检索 (Hybrid Search)

  • 问题：单纯的向量检索可能无法精确匹配关键词（如产品型号、人名），导致召回内容语义相关但事实错误。
  • 解决方案：
    • 结合**关键词检索（如 BM25）*和*向量检索。关键词保证了精确匹配，向量保证了语义匹配。
    • 使用**倒排秩融合（RRF）**等算法合并两路结果，得到更可靠的候选集。

4. 查询重写/转换 (Query Transformation)

  • 问题：用户的原始查询可能过于简单、模糊或复杂。
  • 解决方案：
    • 多查询召回 (Multi-Query Retrieval): 让 LLM 将用户的原始查询扩展成多个不同角度、更具体的子查询，然后分别进行检索，合并结果。
    • HyDE (Hypothetical Document Embeddings): 让 LLM 先根据用户问题生成一个“假设性”的理想答案，然后用这个答案的 Embedding 去检索，通常能找到更相关的内容。

5. 引入重排器 (Re-ranker)

  • 问题：初步检索（召回）回来的 Top-K 个文档块可能包含很多“噪音”。
  • 解决方案：
    • 在召回和生成之间增加一个**重排（Re-ranking）**阶段。
    • 使用更强大但计算量也更大的模型（如 Cross-Encoders）对召回的 Top-K 文档进行重新打分，筛选出与查询真正相关的几个文档块送入 LLM。这能极大地过滤掉干扰信息。

阶段二：事中控制 —— 优化生成过程

当检索回来的上下文质量已经很高了，我们还需要“管住”LLM，让它更忠实于给定的信息。

1. 强化提示工程 (Prompt Engineering)

这是最直接、成本最低的方法。

  • 问题：简单的提示无法约束 LLM 的行为。
  • 解决方案：在 Prompt 中给出非常明确的指令。
    • 限定信息来源：“你必须且只能使用下面提供的‘上下文’来回答问题。”
    • 定义未知情况：“如果上下文中没有足够的信息来回答问题，请直接回答‘根据我所掌握的资料，无法回答您的问题’，不要自己猜测。”
    • 要求引用：“在回答时，必须注明信息来源于哪一段原文（引用溯源）。”

场景 1：“我什么时候应该坚守 PGVector？”

  • 条件：
    • 你的向量数据量不大（百万级到千万级）。
    • 查询 QPS 不高，且对延迟不那么敏感（百毫秒级可接受）。
    • 你的查询逻辑里，元数据过滤条件很简单（比如只有一个 WHERE user_id = ?）。
    • 你的团队技术栈单一，引入新中间件的审批流程复杂，或运维人力紧张。
    • 架构极简，零额外学习与运维成本 (Zero-Friction Adoption)
      • 本质： 它只是 PostgreSQL 的一个插件。
      • 优势： 不需要引入、部署和维护任何新的分布式中间件。团队现有的 SQL 知识、ORM 框架（JPA/MyBatis）、备份工具、监控体系全部100% 直接复用。这让项目能够以极低的门槛快速启动。
    • 绝对的数据一致性保障 (ACID Transactions)
      • 本质： 向量数据只是关系型表中的一个普通字段（VECTOR 类型）。
      • 优势： 彻底告别“业务数据存 MySQL，向量数据存 Milvus”带来的分布式事务噩梦。你可以在同一个数据库事务中，同时对用户的业务信息和向量特征进行原子性的 INSERT/UPDATE/DELETE。要么全成功，要么全回滚，保证了数据逻辑的绝对安全。
    • 无缝融合的复杂混合查询 (Powerful Hybrid Search)
      • 本质： 背后是强大的 PostgreSQL 关系型查询引擎。
      • 优势： 真实的 RAG 场景往往需要极其复杂的过滤条件（比如：按用户 ID 隔离、多表 JOIN 筛选状态、按时间段过滤等）。PGVector 允许你用最熟练的 SQL 语法，在一行代码里同时完成复杂的结构化数据过滤和高维向量的相似度计算。这种关系型数据与向量数据的深度结合，是很多专用向量数据库的软肋。
    • 极佳的成本效益与架构演进起点 (Cost-Effective & Evolutionary)
      • 本质： 复用现有硬件资源，无需额外采购机器。
      • 优势： 在项目初期或数据量中等（百万级）时，它是性价比最高的方案。即使未来业务爆发，数据量上亿导致 PGVector 出现性能瓶颈，也可以平滑地将其作为业务库，再将向量计算部分迁移到专业的 Qdrant 或 Milvus 中。这是一种极具弹性和低风险的渐进式架构演进策略。
  • 决策： 继续使用 PGVector。 在这个舒适区内，它的便捷性带来的收益，远大于它在性能上的妥协。

场景 2：“我什么时候应该考虑从 PGVector 迁移到 Qdrant？”

  • 条件：
    • 你发现带多个复杂 WHERE 条件的向量查询，延迟飙升到秒级，已经成为系统瓶颈。例如：“找出过去 7 天内，由 A 部门创建，且包含‘AI’标签的所有文档的相似内容”。
    • 你的内存成本压力巨大。你想在不显著牺牲精度的前提下，用更少的内存装载更多的向量（Qdrant 的标量量化能将内存占用降低 4 倍）。
    • 你追求极致的低延迟，希望 P99 响应时间控制在 50ms 以内。
  • 决策： 优先迁移到 Qdrant。 它强大的 Pre-filtering 能力和出色的资源效率，能完美解决 PGVector 在这些场景下的痛点。对于大部分从 PGVector 升级而来的中等规模应用，Qdrant 是性价比最高的选择。

    • 你的公司有成熟的 K8s 运维体系，能够驾驭一个复杂的分布式系统。

RAG数据源如何解决时效问题，知识过期了怎么办

“仅仅能同步还不够，关键是在向量数据库中如何精准地找到并替换掉那块‘过期的小抄’。这极其依赖我们在存入数据时的元数据（Metadata）设计。

  1. 强绑定 doc_id 与 chunk_id
    • 痛点：如果你只是把一段段文本（Chunk）塞进向量库，当一篇文档更新时，你根本不知道该删掉库里的哪些向量。
    • 方案：在切块存入时，必须给每个 Chunk 打上元数据标签：{“source_doc_id”: “file_123”, “chunk_index”: 5, “last_updated”: “2024-05-20”}。
    • 更新逻辑 (Upsert)：当 file_123 被修改时，系统先去向量库里执行一个 DELETE WHERE source_doc_id = ‘file_123’，把旧的所有切块全部删干净；然后再把重新解析的新切块 INSERT 进去。这样就完美避免了新旧知识的冲突。
  2. 引入 TTL (Time-To-Live) 自动过期机制
    • 场景：对于一些天然具有极短生命周期的数据（比如：“今天下午三点的会议纪要”、“双十一当天的临时促销规则”）。
    • 方案：很多现代向量数据库（如 Milvus, Qdrant, Redis）都支持给数据设置 TTL。我们在入库时直接带上过期时间，时间一到，数据库底层自动物理删除这些数据，连同步的逻辑都省了，极其优雅。

    • 这是一个非常高阶的玩法。如果不强制过滤，而是希望越新的文档权重越高。

. 重排模型（Reranker）的原理是什么？（Cross-Encoder 交叉注意力原理）

  • 它是基于 Transformer 的 交叉编码器（Cross-Encoder） 架构。
  • 底层机制：它不生成向量。它将 Query 和 Document 拼接成一整句话送入模型。例如：[CLS] 用户问题 [SEP] 候选文档内容 [SEP]。
  • 深层化学反应（Self-Attention）：在 Transformer 的每一层网络中，Query 中的每一个字都会和 Document 中的每一个字进行计算（这就是大名鼎鼎的 Self-Attention 注意力机制）。
  • 为什么它准？ 因为它能理解上下文的“动态纠缠”。
    • 举例：Query 是“苹果公司的利润”，Doc 是“这台榨汁机能榨苹果，公司利润很高”。
    • 在粗排（向量）中，因为“苹果”、“公司”、“利润”词汇全命中，相似度可能极高。
    • 在精排（Reranker）中，注意力机制在逐字审视时，会发现 Doc 里的“苹果”修饰的是“榨汁机”，与 Query 中的“苹果公司”这个整体实体在语义矩阵上对不上号，因此会在输出层给出极低的分数（趋近于 0）。

HNSW与IVF

IVF (Inverted File) 倒排文件索引

1. 底层原理

IVF 的思想完全借鉴了传统搜索引擎的“倒排索引”（从单词找到包含该单词的文档列表）。在向量领域，它变成了：从“聚类中心”找到“属于该聚类的向量列表”。

  • 建索引阶段 (Training & Building)：
    1. 聚类 (Clustering)： 从海量数据中随机抽取一部分样本，使用 K-Means 等聚类算法，将整个向量空间划分为 nlist 个区域。每个区域的中心点被称为质心 (Centroid)。
    2. 分配 (Assigning)： 遍历所有的向量，计算每个向量与所有 nlist 个质心的距离，然后将该向量放入距离最近的那个质心所代表的“桶（Bucket）”里。
  • 查询阶段 (Searching)：
    1. 定位桶： 将查询向量（Query Vector）与所有 nlist 个质心进行比较，找出距离最近的 nprobe 个质心。
    2. 桶内搜索： 只在这 nprobe 个桶内，进行精确的、暴力的距离计算，找出最终的 Top-K 相似向量。

痛点场景： 以前老系统叫 Alpha，里面沉淀了大量有价值的底层设计文档。现在系统升级或改名了，对外统一叫 Omega。用户提问：“Omega 系统的底层架构是什么？” 如果直接拿去查向量，可能根本搜不到旧文档里 Alpha 的高价值内容。

在构建知识库时，文本切块策略至关重要。你会如何选择合适的切块大小和重叠长度？这背后有什么权衡？

核心回答策略：不要给出一个“万能数字（比如 512 token）”，而是要根据“模型上下文窗口、用户提问习惯、数据固有结构”三个维度来动态选择，并深刻剖析“块太大 vs 块太小”的致命博弈。

你可以这样回答：

“文本切块（Chunking）是 RAG 知识库构建的第一步，也是最容易被忽视的一步。如果切得不好，后续的向量检索和 LLM 生成都会变成‘灾难’。

在选择合适的切块大小（Chunk Size）和重叠长度（Overlap/Stride）时，我没有一个固定的公式，而是基于以下几个维度的权衡（Trade-off）：

1. 切块大小 (Chunk Size) 的权衡与选择

  • 太小的 Chunk（如 100-250 Tokens）：
    • 优势： 向量表达极其精准（高内聚）。当用户搜索一个具体概念时，很容易通过余弦相似度匹配到这个小块。同时，喂给 LLM 时占用的 Context 很少，成本低、速度快。
    • 劣势（致命伤）： 严重丧失了上下文语境（Context Loss）。比如一句话“他是个好人，但他今天杀了人”，如果被切成了两块，检索到第一块时，LLM 就完全得出了相反的结论。
  • 太大的 Chunk（如 1000-2000 Tokens）：
    • 优势： 保留了非常完整的上下文，LLM 在阅读理解时不容易出现断章取义的幻觉。
    • 劣势： 向量表达变得“模糊（Diluted）”。一个大块里可能包含了 A、B、C 三个不同的主题，它的向量中心点可能哪个都不挨着。当用户精确提问 A 时，这个大块的相似度得分反而拼不过那些只讲 A 的小块，导致召回率（Recall）下降。此外，大块极其消耗 LLM 的输入 Token 成本和推理时间。

我的选择策略（实战经验）：

  1. 看基座模型能力： 如果我用的模型上下文窗口极短（比如早期的 4K 模型），我只能切 300-500 tokens。如果我用的是支持 128K 甚至 1M 的模型（如 Claude 3 或 Kimi），我会倾向于切得稍微大一些（800-1000 tokens），优先保证上下文完整。
  2. 看数据固有结构（最推荐的做法）： 我不会简单粗暴地按固定字数去切（Fixed-size Chunking）。我会使用基于语义和文档结构的切分（Semantic/Structural Chunking）。比如，通过 Markdown 的标题（#, ##）、段落（\n\n）或者 HTML 的 DOM 树来切。这保证了一个 Chunk 至少是一个完整的逻辑段落。

2. 重叠长度 (Overlap Size) 的权衡与选择

  • 为什么要重叠？ 为了修补被强行切断的上下文。比如一句话正好卡在两个 Chunk 的边界上，如果不重叠，这句话的语义就支离破碎了。
  • 太短的 Overlap（如 0-5%）： 起不到粘合上下文的作用。
  • 太长的 Overlap（如 50%）： 导致知识库急剧膨胀，存储成本和向量检索的计算量翻倍，且在最终拼接到 Prompt 时会引入大量重复废话，干扰 LLM。

我的选择策略（实战经验）：
通常我会将重叠长度设置在 Chunk Size 的 10% 到 20% 之间（比如 Chunk 是 500 tokens，Overlap 就设为 50-100 tokens）。这通常能恰好覆盖一个长句子的长度，足以保证相邻块之间的逻辑过渡。

如何选择一个合适的嵌入模型？评估一个 Embedding 模型的好坏有哪些指标？

1. 核心选型考量维度 (How to Choose)

  1. 语言能力 (Language Support)：
    • 如果我的知识库全是中文，或者包含大量中英文混排的术语，我绝对不能盲目使用只在英文语料上训练的开源模型。我会优先选择针对中文优化过的模型（如 BGE 系列，或智谱、百川的商用 Embedding）。
  2. 支持的最大上下文长度 (Max Sequence Length)：
    • 很多经典的开源模型（如早期的 BERT 系列）最大只支持 512 Tokens。如果我的 Chunk Size 设了 1000，强行喂给这些模型，后面的 488 个 Tokens 会被直接无情截断丢弃，导致严重的特征丢失。因此，我必须选择支持至少 8192 甚至更高 Tokens 的长文本 Embedding 模型（如 Jina Embedding 或 OpenAI 最新模型）。
  3. 向量维度大小 (Dimensionality) 与存储成本：
    • 维度越高（如 OpenAI 的 1536 维 或有些 3072 维），表达的语义越丰富，理论上越准。
    • 代价： 但在处理千万级文档时，1536 维的向量库对内存（RAM）的消耗极大，检索速度也会变慢。如果成本受限，我会选择一些维度较低（如 768 维或甚至 384 维）但经过深度优化的模型，或者在存入向量库前使用 PCA 等降维技术。
  4. 是否支持查询与文档的不对称映射 (Asymmetric Retrieval)：
    • RAG 场景是一个典型的不对称检索：Query 通常是一句很短的问句（如“怎么报销？”），而 Document 是很长的一段说明文档。一些模型（如 Instruct 类的 Embedding）专门为此做了优化，允许在 Query 前面加上特定前缀（如 Represent this sentence for searching relevant passages:），这能显著提升召回率。

2. 评估模型好坏的指标 (How to Evaluate)

如果要在几个候选模型中做最终决定，我不会只看官方宣传，而是会看客观指标并结合业务数据进行评测：

  1. 参考权威榜单 (MTEB / C-MTEB Leaderboard)：
    • 这是目前业内公认的 Massive Text Embedding Benchmark（海量文本嵌入基准测试）。我会重点看其中的 Retrieval（检索） 任务得分，而不是聚类或分类得分。同时如果是中文业务，必须看 C-MTEB 榜单。
  2. 核心评价指标：
    • NDCG@10 (归一化折损累计增益)： 这是衡量搜索引擎排序质量最核心的指标。它不仅看你有没有找对（召回），更看重你是否把最相关的文档排在了最前面。在 RAG 中，如果正确文档排在了第 10 名，很可能因为 Context 窗口限制根本送不到 LLM 嘴里，所以排名极度重要。
    • MRR (平均倒数排名)： 评估第一个正确答案出现的位置有多靠前。
    • Recall@K (召回率)： 在返回的 Top-K 个结果中，包含了多少应该被找出来的相关文档。
  3. 构建私有评测集 (Golden Dataset - 最关键的一步)：
    • 公有榜单得分高，在私有业务上未必好（特别是涉及大量公司内部黑话、缩写或特殊行业术语时）。
    • 我会在正式选型前，人工（或用 LLM 辅助）构建几百个真实的 (Query, 预期的正确文档) 对。然后用几个不同的 Embedding 模型跑一遍检索，计算它们在我们自己数据上的 NDCG 和 Recall。这才是决定最终选型的唯一真理。”

如果rag检索的一些东西，不符合或者语义相识但是词意不同怎么办，还有就是RAG能不能解决一些幻觉的问题

1. 检索不准怎么办？（“语义相似但词意不同”）

  • 问题：向量检索（Vector Search）是基于语义距离的。
    • 例子：用户问“苹果公司股价”，可能检索出“好吃的红富士苹果”，因为“苹果”这个词语义接近。
    • 例子：用户问“不推荐买哪款车”，可能检索出“强烈推荐买这款车”，因为语义上都在聊“买车建议”。
  • 解决方案（组合拳）：
    1. 混合检索 (Hybrid Search)：这是标配。
      • 同时用向量检索（找意思相近的）和关键词检索 (BM25)（找字面完全匹配的）。
      • 用 RRF (Reciprocal Rank Fusion) 算法把两者的结果融合，能极大过滤掉那种“语义像但字面完全不搭”的错配。
    2. 重排序 (Re-ranking) —— 最有效：
      • 在初步召回（比如 50 条）后，用一个专门的 Cross-Encoder 模型（如 BGE-Reranker）对这 50 条进行精细打分。
      • 重排序模型比向量模型更聪明，能读懂“不推荐”和“推荐”的逻辑区别，把真正相关的排到第一位。
    3. 元数据过滤：加上 category=”tech” 标签，直接过滤掉水果类的文档。

2. RAG 能不能解决幻觉？

能大幅缓解，但不能 100% 根除。

  • RAG 是怎么治幻觉的？
    • 限制范围：我们在 Prompt 里告诉 LLM：“你必须只根据我给你的这些资料回答，不知道就说不知道。”
    • 提供事实：LLM 瞎编通常是因为它脑子里没干货。RAG 把真凭实据（Context）喂到嘴边，它自然就老实了。
  • 为什么还会通过 RAG 产生幻觉？
    1. 检索错了（Garbage In, Garbage Out）：如果检索出来的文档本身就是错的，或者是不相关的，LLM 基于错误信息一本正经地回答，这也是幻觉。
    2. 冲突：检索到的两段文档说法不一，LLM 可能会“脑补”一个折中方案。
    3. 大模型本性：即使资料在手，有些模型（尤其是参数量小的）还是会习惯性地添加一些“漂亮的废话”或脑补细节。

RAG 的标准流程通常是：

  1. 全量库 (100万)
    ↓
  2. 粗召回 (Recall)：用向量或关键词，快速捞出 Top 100。
    ↓
  3. 精排序 (Re-ranking)：用更聪明但更慢的模型（Cross-Encoder），仔细读这 100 篇，打分，选出 Top 5。
    ↓
  4. 给大模型：把这 5 篇喂给 LLM 生成答案。
